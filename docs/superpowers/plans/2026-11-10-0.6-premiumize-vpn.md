# 0.6 Premiumize VPN Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `subagent-driven-development`. This plan
> states contracts, behaviour and constraints — **it deliberately contains no implementation or
> test bodies**. Read the file you are modifying before writing anything; the plan tells you what
> must be true, the codebase tells you how to say it.

**Goal:** Kevin switches on a Premiumize VPN for one KevBox Live customer in kevbox.dev and picks its server; that customer's TV then sends KevBox Live's own traffic through an OpenVPN tunnel, falls back silently to normal internet after a failed cycle, pings Kevin on Telegram, and tries again 3 hours later.
**Architecture:** The TV embeds the OpenVPN for Android engine (ics-openvpn, GPLv2) behind a small `VpnEngine` interface. A pure rules machine (`VpnRules`) decides every connect, wait, server change and fall-back from inputs and a clock; a runner (`VpnController`) carries out its actions, `ManagedVpn` feeds it the chosen playlist's VPN like `ManagedProxy` does, a Realtime subscription makes kevbox.dev changes land in seconds, and a saved queue reports VPN events. kevbox gets migration `0023_live_vpn.sql`, shared VPN pieces, a VPN servers page, a switch in the customer window, login upkeep in the debrid actions and the 15-minute refresh job, and VPN messages in the 5-minute watch check.
**Tech stack:** Kotlin, Koin, Core 1.0.69 (unforked; read-only source at `/home/kevin/projects/OwnTV/build/kevbox/core-1.0.69/OwnTV_Core-core-1.0.69/`), ics-openvpn (pinned tag, built once on this PC), OkHttp WebSocket, JUnit 4; kevbox: Next.js 16, `pg`, Supabase (Postgres 17; disposable test container postgres:16), vitest, Node 25.9.0, shadcn parts in `kevbox:src/components/ui/`, `@base-ui/react` Switch.
**Spec:** `docs/superpowers/specs/2026-11-10-0.6-premiumize-vpn-design.md`. Cite its criteria as `AC-n`.
**Size:** 13 tasks. Spec `Size:` keeps the phase whole at 41 criteria.

```kotlin
// kevbox/vpn/VpnEngine.kt
sealed interface EngineEvent {
    data object Up : EngineEvent        // tunnel established
    data object Down : EngineEvent      // was up, is no longer (a drop; the engine may still be reconnecting)
    data object Failed : EngineEvent    // gave up on its own: login refused, config refused, process ended
}
interface VpnEngine {
    /** Starts connecting and returns at once. [config] is the server's raw `config` column. */
    fun start(host: String, config: String, username: String, password: String)
    /** Stops and tears the tunnel down; safe to call when idle. Emits nothing. */
    fun stop()
    val events: kotlinx.coroutines.flow.SharedFlow<EngineEvent>
}

// kevbox/vpn/OvpnConfig.kt
/** Pure. The config the engine receives: Premiumize's file adapted to the app's retry rules. */
fun prepareOvpn(raw: String): String
```

**Behaviour:**
1. **Canary first, before any Kotlin.** Pin one ics-openvpn release tag (the newest whose OpenVPN core is 2.6.x). Build its engine module for `arm64-v8a`, `armeabi-v7a` and `x86_64` with OpenVPN 2.x only (no OpenVPN 3 library, which needs SWIG and adds size), native libraries stripped at build time (the app's `keepDebugSymbols += "**/*.so"` means AGP strips nothing). Add it to the app, then run `gradle-locked.sh assembleStandardRelease assembleX86_64Release`. The canary passes when both build, each APK holds the engine's `.so` files for exactly its ABIs, R8 leaves the engine's JNI and AIDL classes intact, and the `standard` release APK is at most 61,776,028 + 15,000,000 = 76,776,028 bytes (AC-22; "15 MB" read as 15,000,000 bytes, the stricter reading). Record both APK sizes and the engine's share in the commit message body.
2. Route choice, in this order. **Route A (preferred): a prebuilt AAR** made by `build-engine.sh` on this PC from the pinned tag (its skeleton/library flavour), committed under `extras/openvpn/`, added in `app/build.gradle.kts` as a local file dependency, with any runtime library it needs that the app lacks declared inline there. NDK and CMake then stay out of every app build. **Route B (fallback): a vendored module**: the engine's Gradle module at the pinned tag as `:openvpn` (in `settings.gradle.kts`), its native build using the NDK already on this PC (`~/Android/Sdk/ndk/27.1.12297006` or newer, pinned by `ndkVersion`) and SDK CMake. Decision rule: take Route A unless it fails one canary check after a real attempt (the AAR will not build, does not link in a flavour, R8 or manifest merge breaks it beyond a keep rule or a `tools:node` fix, or its size passes the limit); then Route B. If Route B also fails a canary check, or the size limit cannot be met by dropping OpenVPN 3 and stripping, **stop the lane and report** what failed with the numbers; no later OwnTV task starts on a guess. Never take a third-party prebuilt from Maven Central or JitPack: unknown binaries, usually stale OpenVPN.
3. The manifest declares the engine's VPN service with `android:permission="android.permission.BIND_VPN_SERVICE"`, the `android.net.VpnService` intent filter and the foreground-service type the pinned engine's own manifest uses; the engine's activities, if merged, are removed with `tools:node="remove"` so nothing of its UI can open (AC-34).
4. `IcsVpnEngine.start` parses `prepareOvpn(config)` with the engine's own config parser into a temporary profile (never saved in the engine's profile list), sets the login from `username`/`password`, sets the allowed-apps list to exactly the app's own package in "allowed" mode, so the engine calls `VpnService.Builder.addAllowedApplication` for it alone (AC-27), and starts the engine's service. `stop` stops it through the engine's service binding. Engine state changes map to `EngineEvent`: connected → `Up`; not connected after `Up` → `Down`; login refused, parse error or service death → `Failed`; every connecting state → nothing.
5. Before the first start, `IcsVpnEngine` creates every notification channel the engine posts to, with the engine's channel ids, importance `NotificationManager.IMPORTANCE_MIN` and the name string below (AC-34). A channel's importance is fixed at creation, so this runs before the engine ever creates them.
6. `prepareOvpn`: removes an inline `<auth-user-pass>…</auth-user-pass>` block (the login comes from the profile); replaces `resolv-retry infinite` with `resolv-retry 25` (the controller's 30-second rules decide, AC-30); when no `data-ciphers` line exists, adds `data-ciphers AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305:AES-256-CBC` and `data-ciphers-fallback AES-256-CBC` (Premiumize files say `cipher AES-256-CBC`, which an OpenVPN 2.6 core no longer negotiates by itself). Every other line, the `<ca>` block and `verify-x509-name` stay byte for byte. Line endings in, line endings out.

**Behaviour:**
1. `Wanted(want)` with a want, in this order: (a) a fall-back in force for the same `server` → nothing until it is due; (b) `otherVpnActive` → `Report(OTHER_VPN_ACTIVE)` once per blocked stretch (again only after a `Wanted` found it clear, or in a new process), nothing else (AC-29); (c) no permission → `AskPermission` when in the foreground and not refused for this exact want in this process, otherwise wait (a `Foreground` re-runs this step) (AC-26); (d) otherwise start a cycle.
2. Starting a cycle: `SaveFallback(null, null)`; with `auto`, `PickServers`, then `Picked` fixes main and backup for the whole cycle (AC-41); otherwise main = `server`, backup = `backup`. Then `Connect(main)` with `dueAtMs = now + 30 s`.
3. `EngineUp` while connecting → connected: `Report(CONNECTED, host)`, `RestartChannel`, no due (AC-28, AC-40). `EngineFailed`, or `Tick` past the 30 s → `Disconnect` and one failure (AC-28, AC-30).
4. A cycle changes server at most once.
5. `EngineDown` while connected → `dueAtMs = now + 30 s`; `EngineUp` before then → connected again with no report; `Tick` past it → `Disconnect`, `RestartChannel`, then a new cycle after a 60-second wait, on the main server (with `auto`, after a fresh pick); when the dropped server is that cycle's main, the drop counts as its first failure (AC-30).
6. Fall-back in force: `dueAtMs = at + 3 h`. Due when `now >= at + 3 h` or `now < at` (the TV clock went back past it). When due and the latest want still names the same server and the app is in the foreground → new cycle; due while paused in the background → on `Foreground` (AC-32). A new process restores the stored time through `initial`, so a restart does not start early.
7. `Wanted(null)` or `SignedOut` → `Disconnect` if anything runs, `RestartChannel` if the tunnel was up, `SaveFallback(null, null)`, forget the refusal (AC-33). A want whose `server` differs from the current one (or a different `clientNumber` with a different server) → the same stop, then a new cycle at once. A change of only `username`, `password` or `backup` → nothing now; the next `Connect` uses the new values (a backup change only if the cycle has not yet changed server).
8. `Permission(true)` → start a cycle. `Permission(false)` → `Report(PERMISSION_DENIED)`, remember the refused want; no further prompt in this process until a `Wanted` brings a different want (AC-26).
9. `Background` → `dueAtMs = now + 10 min` for the pause (kept with any other due as the earlier of the two). Reaching it → `Disconnect` with no failure, no report, `RestartChannel` not needed (nothing plays), fall-back time untouched; the state remembers what it was doing. `Foreground` before then → cancels the pause. `Foreground` after a pause → connected before: `Connect(last used host)` (a failure there is handled as the drop in item 5); mid-cycle: an immediate try on the cycle's current server with its counts kept; fall-back in force: nothing until due (AC-37).
10. `RestartChannel` appears exactly when the tunnel goes from down to up or from up to down while the app is in the foreground; stops of tries that never came up change no route and restart nothing.

- The first try on the backup also waits 60 seconds: the conservative reading of AC-30, in line with Premiumize's rule on frequent server changes.
- With `auto` and only one server answering, there is no backup for that cycle (AC-41 names the second lowest; there is none).
- Pure: no Android, no coroutines, no clock reads; `nowMs` comes in. `FallbackStore` is the only persistence (prefs name `kevbox_vpn`, keys classified as `preference-key`), written by the runner on `SaveFallback`. Fall-back time is wall clock because it must survive a restart.

2. While signed in, the socket opens and joins with a fresh `accessToken()`; a heartbeat goes out every 25 s; a new token goes out every 30 minutes as an `access_token` frame. A token read that fails counts as one failed attempt.
3. `Change` calls `onChange()` (the coordinator's `onPlaylistChanged`); after every successful (re)join it also calls it once, so a change made while the socket was down is not missed.
4. `onPlaylistChanged` starts a playlist check within 5 seconds. If a check is already running, one more check starts as soon as it ends (at most one waiting), so the TV always reads the row after the change (AC-33, AC-39). The 15-minute check and the check on return to the front stay as they are.

**Constraints:**
- No new dependency: OkHttp's `WebSocket` is already on the classpath. The socket uses the shared client with the same direct-connection rule as `SupabaseApi` (`Proxy.NO_PROXY`): kevbox.dev must stay reachable when the customer's proxy is down. While the VPN tunnel is up, the app's own traffic goes through it anyway (AC-27).
- Nothing logs a frame, the token, the user id or the URL's key; logs carry state names only.
- The payload is never read for data. The row's columns, the password included, are only fetched by the playlist check.
- Deviation from the spec's scope list, stated: `KevBoxAuth.kt` gains `accessToken()`; `signedInCall` cannot hand out a token for a socket that lives longer than one call.
