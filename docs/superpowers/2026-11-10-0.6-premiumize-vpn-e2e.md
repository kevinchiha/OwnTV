### Notes

1. **Android's prompt opens with no button focused.** On this emulator the first remote key on
   `com.android.vpndialogs/.ConfirmDialog` only gives a button focus; OK pressed straight away does
   nothing, and D-pad down lands on Cancel. This is Android's own dialog, not the app's. A customer
   who presses OK twice will be fine; one who presses down and then OK refuses the VPN and Kevin
   gets the "didn't allow the VPN" message. Worth watching during the live test on a real TV.
2. **No channel restart after this fall-back.** The panel saw one stream request (12:35:55) for
   the whole run. The tunnel never came up in (c) or (d), so the route never changed and nothing
   needed re-tuning; AC-40's restart "within 3 seconds of the new connection being ready" could not
   be exercised without a working tunnel. It belongs to the live test.
3. **The status notification's importance.** The app creates the engine's three notification
   channels at `IMPORTANCE_MIN` (`openvpn_bg` and `openvpn_userreq` read `mImportance=1` in `dumpsys
   notification`). `openvpn_newstat`, the channel of the engine's foreground-service notification,
   read `mImportance=2` (low) while the engine ran: Android raises a channel that carries a
   foreground service's notification to low, since a minimum-importance notification may not back
   a foreground service. Low is therefore the lowest Android allows for the service, which is what
   AC-34 asks. The notification itself is Android's, not a toast, dialog or banner, and the
   uiautomator dumps never showed it on screen.
4. **Nothing secret in the logs.** The logcat capture of the whole run held no `pass1`, no
   `192.0.2`, no `vpn-test`, no `BEGIN CERTIFICATE`, no `auth-user-pass`, no `access_token` and no
   `eyJhbGci`. The app's own lines were `OpenVPN : Starting openvpn`, `OpenVPN process exited` and
   `Exiting`.
5. **Two playlist reads per change.** Both off/on runs in (d) caused two playlist reads in the
   same second: each committed statement is a change event, and the coordinator runs one more check
   after a running one (Task 5). Run 1's statements committed 11 ms apart, so I cannot tell from the
   gateway log whether one read saw the off row; run 2's single transaction removes the question.
6. **The 15-minute check ran once** (playlist read at 10:51:32, mid-cycle) and changed nothing,
   as it should: the row's `vpn_changed_at` had not moved.

## What this run cannot prove

- **A real tunnel.** Every try went to TEST-NET addresses that never answer, so no `connected`
  event, no drop inside a working tunnel (the 30-second grace), no channel restart after the
  tunnel comes up (AC-40) and no 10-minute off-screen disconnect with a reconnect (AC-37) happened
  here. Task 3 and Task 4's unit tests cover those rules with a fake engine.
- **AC-27's address check.** Only KevBox Live's traffic in the tunnel needs a tunnel to a real
  Premiumize server and an address-echo request from the app's user and from `adb shell`.
- **Premiumize's login rules.** Whether Customer ID and API key log in, how many connections one
  account allows at once, and whether `proto tcp` on port 443 connects all need Kevin's debrid
  login, which no task uses.
- **The other half of AC-38.** With one test member, check (a) proves only that the member gets
  their own row's changes, not that no other member gets them. kevbox Task 7's SQL tests cover
  that half (the subscription's row filter and policies).
- **"Automatic (fastest)".** The ping pick (AC-41) was not run: the test hosts have no addresses to
  ping. `PingerTest` and `VpnControllerTest` cover it.
- **Telegram.** No Telegram variable was set and no kevbox.dev server ran, so the `fell_back`
  rows kept `telegram_sent_at` null. Task 12's tests cover the messages.

All of these are the live test in the plan's "After the build" section
(`docs/superpowers/plans/2026-11-10-0.6-premiumize-vpn.md`), with Kevin present, before any release.
