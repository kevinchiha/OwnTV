# 0.3-error-reporting — design

## Goal

Kevin learns about KevBox Live crashes, freezes, playback errors and playlist or guide failures
from Sentry and kevbox.dev, without a member calling him. Every error code TiviMate shows has a
KevBox Live equivalent, and nothing from KevBox Live mixes with KevBox TV's errors.

## Scope

- **OwnTV app (`kevbox/` layer, branch base `kevbox-live`)**: Sentry Android SDK with native
  crash and freeze capture; a new error reporter (`kevbox/errors/`) that listens to both players'
  failure feeds, Core's playlist syncs and guide downloads, runs the account check, maps each
  failure to a code, dedupes, queues on disk and sends batches to Supabase; build wiring for the
  Sentry key and symbol upload (`app/build.gradle.kts`, `release.sh`); `UPSTREAM-SYNC.md` entry.
- **kevbox (branch base `main`)**: migration `0015_live_error.sql` (table, write function,
  cleanup function); admin reads and API routes; the daily prune route; the KevBox Live box in the
  customer window gets an errors list; a new dashboard page, "Live errors".
- **Docs**: a short how-to for creating the Sentry project and where its key goes.

The code list the reporter maps to is the research file
`docs/superpowers/2026-10-14-0.3-error-reporting-tivimate-codes.md`, committed with this spec.

## Acceptance criteria

### Sentry: crashes and freezes

- **AC-1** With a Sentry key (DSN) given at build time, an uncaught exception in app code shows
  up in the KevBox Live Sentry project. The event carries app version, TV model, Android version
  and the member's Supabase user id. It never carries the email.
- **AC-2** A native crash (for example a SIGSEGV inside libmpv) shows up in Sentry with a native
  stack trace, on the `standard` flavour (arm64-v8a and armeabi-v7a) and on `x86_64`.
- **AC-3** A main-thread freeze of 5 s or more shows up in Sentry as an ANR (app not responding)
  event.
- **AC-4** With no Sentry key, the app builds, starts, and never initialises Sentry or contacts
  any Sentry host. A unit test covers the "no key" path.
- **AC-5** Each Sentry event carries the last 20 error-reporter entries as breadcrumbs (code,
  raw status, channel name, engine, time), with no address and no credential.
- **AC-6** A scrubber runs on every Sentry event before it leaves the TV. It replaces anything
  shaped like a URL with `[url]` and removes the current playlist's Xtream username and password,
  the member's email and any Supabase token. A unit test feeds it an event holding all of these
  and checks that none survive.
- **AC-7** Sentry tracing, profiling and session replay are off (sample rate 0). Only errors and
  ANRs get sent.
- **AC-8** Core's `CrashRecorder` still writes its crash file on the TV after Sentry is
  installed: Sentry's handler hands the crash on to the one already installed.
- **AC-9** A release build with `SENTRY_AUTH_TOKEN` set uploads the R8 mapping file, so Java and
  Kotlin stack traces in Sentry show real class and method names. It also uploads the app's native
  libraries, so Sentry matches each native frame to its library. Core's libmpv and ffmpeg
  libraries ship stripped, so their frames show library and offset, plus exported function names
  where the library has them. Without the token, the release build still succeeds and skips the
  upload.

### Error reporter on the TV

- **AC-10** KevBox Live plays live channels on Core's `LivePreviewEngine` (ExoPlayer, one engine
  that moves between the guide's top box and full screen), and catch-up and mpv handovers on
  `OwnTVPlayer` (mpv, with an ExoPlayer fallback). Every time either engine's failure feed
  (`errorInfo`) goes from empty to a failure the member sees (the channel doesn't play), the
  reporter records one entry. Core sets `errorInfo` only after its own retries give up, so a
  failure Core recovered from by itself (engine switch, software fallback, a retry that played)
  records nothing. The entry holds: code, raw HTTP status (or none), error name, engine (`exo` for
  `LivePreviewEngine`; for `OwnTVPlayer`, `mpv` unless `isExoActive()`), where it happened
  (`preview` while the video window sits in the guide's top box, `full` anywhere else), live
  flag, channel name, category name, proxy on or off, provider host name (host only, never path
  or query), TV model, Android version, app version, time. The error name is what TiviMate shows
  when there is no status, read from `ErrorInfo.raw` (text; Core passes no exception): the Media3
  error-code name when `raw` starts with one (`ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED` is
  TiviMate's `UnrecognizedInputFormatException`, `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED` its
  `HttpDataSource$HttpDataSourceException`), the mpv error string on mpv, else the first line of
  `raw`.
- **AC-11** The code mapping covers every row of the research file's main table. Any 3-digit
  status that `PlayerErrors.httpStatusIn` finds in `ErrorInfo.raw` (ExoPlayer's
  `Response code: N`, mpv/ffmpeg's `HTTP error N`) is kept as the raw number and gives the code
  `http_<n>`, standard or not (403 → `http_403`, 458 → `http_458`, 884 → `http_884`). With no
  status, the error name and the message in `raw` decide: timeout, DNS failure, refused
  connection, SSL failure, no internet, behind live window, decoder failure, unrecognised format
  and parse failure each get their own code. An mpv failure with no status becomes
  `mpv_load_failed`. Anything else becomes `other`, with the scrubbed message kept. A
  table-driven unit test checks every row of the research table.
- **AC-12** When Core's channel-list sync for the playlist on screen ends
  (`CatalogSyncScheduler.observeSync` goes back to idle) and
  `SourceRepository.getLastSyncStats(sourceId)` holds a `SyncResult.Failed`, the reporter records
  an entry with a `playlist_*` code and the raw status found in the failure message. Core's
  result holds only a message, so the reporter runs the AC-13 account check after each failed
  refresh to name these: wrong login (`auth: 0`), account not active (`user_info.status` Expired,
  Banned, Disabled), too many connections (`active_cons >= max_connections`). The message names
  the rest: rate limited (429), M3U downloads switched off (884), server unreachable,
  channel-list download failed, channel-list parse failed (an object where a list was expected
  included).
- **AC-13** Xtream panels hide the real reason behind 401 or a fake 404. So after a playback
  failure with status 401, 403 or 404, an mpv failure with no status, or a failed playlist
  refresh (AC-12), the reporter runs one account check: the provider's `player_api.php` login
  call through Core's `XtreamClient.fetchAccountStatus` on the TV, which uses Core's HTTP client
  (the same global proxy the player uses) and the playlist's user agent, at most once per 10
  minutes per TV. The entry gets `account_status` (active, expired, banned, disabled,
  wrong_login, unreachable), `active_cons` and `max_connections`. A non-active status replaces the
  code with `account_<status>`, and the raw status stays. The check never opens a stream, so it
  can't take a connection slot. The Xtream username and password stay on the TV; only the three
  result fields go into the entry.
- **AC-14** A guide (xmltv) download or parse that fails records an entry with a `guide_*` code
  and the feed's host name. The reporter reads it from Core's `EpgSourceStore.sources`: a feed
  whose `EpgSource.lastError` changes to a new non-empty value.
- **AC-15** The same code on the same channel within 5 minutes adds to the existing entry's
  `repeat_count` and updates `last_at` instead of making a new entry. After 5 minutes, a new
  entry starts.
- **AC-16** Entries wait in a file on the TV. The file keeps at most 500 entries and drops the
  oldest past that. Entries survive an app restart and get sent once the network and the sign-in
  are back.
- **AC-17** The reporter sends a batch 60 s after the first unsent entry, or as soon as 20 are
  waiting, whichever comes first: one call per batch, at most 50 entries. A failed send retries
  with backoff (1 min, 5 min, 15 min, then every 30 min). A batch the server rejects outright
  (4xx other than 401) is dropped after 3 tries, so one bad entry never blocks the queue.
- **AC-18** With no member signed in, nothing gets sent, and entries stay queued under the
  500 cap.
- **AC-19** Every text field leaving the TV goes through the AC-6 scrubber, and the message is
  cut to 160 characters. A unit test feeds a real Xtream stream address
  (`http://host/live/user/pass/1.ts`) and checks that neither `user` nor `pass` survives.
- **AC-20** The reporter does all disk and network work off the main thread. Recording an entry
  costs the main thread one enqueue, nothing more.
- **AC-21** A test pins the Core contract the reporter depends on (`OwnTVPlayer.errorInfo`,
  `OwnTVPlayer.isExoActive`, `LivePreviewEngine.errorInfo`, `ErrorInfo.reason/raw`,
  `PlayerErrors.httpStatusIn`, `SourceRepository.getLastSyncStats`, `SyncResult.Failed.message`,
  `EpgSource.lastError`, `XtreamClient.fetchAccountStatus`), so a Core update that changes them
  fails the test run before a release.
- **AC-22** The member sees nothing new on screen. The existing on-screen error messages and
  Core's own on-TV error log stay as they are.
- **AC-23** Every change to upstream files carries a `KevBox:` comment saying why, and
  `UPSTREAM-SYNC.md` gets an "Error reporting (0.3)" section listing the hooks to keep on an
  upstream merge.

### Database (kevbox Supabase)

- **AC-24** Migration `0015_live_error.sql` creates `public.live_error` with: id, user_id
  (references auth.users, cascade delete), device_id, first_at, last_at, repeat_count, code,
  http_status (int, null when none), error_name, account_status, active_cons, max_connections,
  engine, surface (`preview` or `full`), live, channel, category, provider_host, proxy, app_version, model, android,
  message_short. It adds indexes on (user_id, last_at desc) and (code, last_at desc), turns RLS
  on, lets members read only their own rows, and gives members no direct write.
- **AC-25** A function `record_live_errors(p_device_id, p_app_version, p_entries jsonb)` takes
  the user id from the sign-in token only. It is a no-op when signed out, takes at most 50
  entries per call, keeps only allow-listed keys with length caps, and replaces URL-shaped text
  with `[url]` on the server side too. The inner function that takes an explicit user id is
  revoked from public, anon and authenticated.
- **AC-26** A member cannot write rows for another member. A test signs in as member A and checks
  that no call creates a row under member B.
- **AC-27** One member can add at most 2,000 rows per day. Entries past that get dropped, and the
  call still succeeds.
- **AC-28** KevBox TV's `member_event`, `record_error` and `prune_telemetry` stay byte-identical.
  The counts in `activity.ts` don't change. A test checks that a `live_error` row never shows up
  in KevBox TV's error counts.
- **AC-29** A function `prune_live_errors(p_days int default 90)` deletes rows whose `last_at` is
  older than that. The same daily timer that runs `prune_telemetry` calls it: the
  `kevbox-telemetry-prune` systemd timer posts to `/api/cron/telemetry-prune`, and that route
  calls `prune_live_errors` after `prune_telemetry`. Only `kevbox_admin` may run it.
- **AC-30** The migration is proven on a local, throwaway Supabase copy, and the file carries a
  rollback snippet that turns the write function into a no-op. It reaches the hosted project only
  on Kevin's explicit word, before the kevbox.dev deploy. During the build, every test runs on
  the local copy and the Android emulator. After Kevin approves the migration and the deploy, the
  TCL plays a dead channel and its 403 shows up in that customer's window within 2 minutes.

### kevbox.dev

- **AC-31** The KevBox Live box in the customer window shows "Errors (last 7 days)": time, code
  with its plain label (for example "403 · Provider refused", or "401 · Account expired" when the
  account check found the reason), the raw status as TiviMate shows it ("code 458") or the error
  name when there is none, channel, ×repeat count, the TV as its model plus the last 4
  characters of its device id ("TCL Smart TV Pro · 3f9a"),
  newest first, at most 50 rows. With no rows it says "No errors in the last 7 days". A customer
  with no KevBox login shows no errors list in the box.
- **AC-32** A new dashboard page, "Live errors", with its own nav item, offers a last 24 h /
  last 7 days switch. It shows (a) codes ranked by total count, each with the number of TVs hit
  and its top 5 channels, and (b) a by-hour list of total errors and TVs hit, so a provider
  outage (many TVs, one hour) stands out from one member's problem (one TV, many hours).
  Clicking a code lists its rows, and clicking a row opens that customer's window.
- **AC-33** Each code's plain label and likely cause (provider account, provider server, network
  or ISP, TV or decoder, app) come from one map in kevbox. The map covers every code the app can
  send, and a test checks that the two lists match.
- **AC-34** Admin reads go through `kevbox_admin` grants and new API routes, with route tests
  for both views and for the empty case.

### Setup

- **AC-35** `docs/kevbox/sentry-setup.md` tells Kevin in plain steps how to create the Sentry
  account and the KevBox Live project, which values to copy (DSN, auth token), and where they go
  (`~/secrets/kevbox-keys/kevbox-live.env`, the secrets file `release.sh` already reads, never
  the repo). `release.sh` exports `SENTRY_DSN` and `SENTRY_AUTH_TOKEN` from that file to Gradle;
  a file without them still releases, with no Sentry. The build runs without a key. Kevin creates the account
  after the build, and the final check on his TCL uses the real key: a test crash, a test freeze
  and a test native crash each show up in the KevBox Live Sentry project.

## Non-goals

- **KevBox TV errors.** KevBox TV keeps its own table and code. This phase neither changes nor
  reads it, at Kevin's word.
- **Changing Core.** The reporter reads Core's public player feed and helpers. Forking Core
  doubles every upstream merge.
- **On-screen changes for the member.** Error messages on the TV stay as Core shows them today.
- **Alerts to Kevin's phone** (Telegram or email when a code spikes). Worth having once the data
  shows what a normal night looks like; a later phase.
- **Sentry performance monitoring, replay, profiling.** These would use up the free plan's quota
  and don't help find errors.
- **Needs Attention for expired or banned accounts.** The account check's findings show in the
  errors list and the Live errors page only. Raising them on Needs Attention changes a page this
  phase otherwise leaves alone; a later phase.
- **Errors the app catches itself in Sentry** (a failed sign-in refresh, a database write that
  throws). Sentry gets crashes and freezes only; playlist and guide failures go through the
  reporter, and caught errors would use up the 5,000-a-month quota.
- **Failures Core recovered from.** Only failures the member sees count (AC-10), to keep the
  pages about real problems.
- **Self-hosted Sentry or GlitchTip.** Kevin picked hosted services before; revisit only if the
  bill becomes a problem.
- **Probing the stream itself to read a status mpv lost.** A probe opens a stream connection, and
  on a one-connection account that probe would itself cause a "too many connections" refusal.
  The account check (AC-13) gets the real reason without opening a stream.
- **Fixing Core's own error classification** (its missing 402, 405–469 and 5xx reasons). The
  reporter keeps the raw status and error name itself, so the gaps in Core's labels lose no
  information.

## Decisions

- Two feeds: Sentry for crashes and freezes, the KevBox Supabase database for playback, playlist
  and guide errors. Rejected: everything in Sentry. The free plan's 5,000 errors a month runs out
  in one provider outage across ~300 TVs, and Sentry can't tie an error to a member's page.
- Approach B, the live reporter on the player's failure feed. Rejected: approach A, reading
  Core's on-TV error log on a timer, because that log keeps only 25 entries and a storm between
  two reads loses the rest.
- A separate table, `live_error`, plus a separate Sentry project. Rejected: an `app` column on
  `member_event`. Kevin asked that the two apps' errors never mix.
- Error codes cover everything TiviMate shows, at Kevin's word ("I want the same"). Research
  found that TiviMate has no code table. It shows "An error occurred: code N" with the server's
  raw status, or the player's exception name when there is none. So every entry keeps the raw
  status and the error name next to our code. Rejected: a fixed list of reasons like Core's,
  which can't hold 453, 469, 884 or the next panel's invented number.
- The account check after 401, 403, 404 or a status-less mpv failure. Xtream panels answer 401 or
  a fake 404 for nearly every refusal, so the status alone can't tell "expired" from "blocked".
  Rejected: trusting the status, which would label most account problems "401".
- Sentry identifies a member by Supabase user id, never email. kevbox.dev can map the id to a
  person; Sentry, a third party, gets no personal data.
- Conventional wisdom: everyone sends every app error to Sentry, because they assume one
  error-tracking tool and a small number of errors. Here, playback errors come in bursts (a
  provider outage hits every TV at once) and need a member link, so they go to the database
  Kevin already runs.
- Grill round 1 (2026-10-14), all on the recommended answer:
  - Sentry account: Kevin creates it after the build; the final TCL check uses the real key.
    Rejected: an account before the build, which the build doesn't need (AC-4).
  - Channel names go to Sentry in breadcrumbs. Rejected: code and engine only. A channel name
    isn't personal, and the member is an anonymous id there.
  - Only failures the member sees count. Rejected: also recording failures Core recovered from,
    which adds noise.
  - Preview box and full screen both count, marked `preview` or `full`. Rejected: full screen
    only, which would miss dead channels found while scrolling the guide.
  - Sentry gets crashes and freezes only. Rejected: also caught exceptions, which spend the quota
    on errors the reporter already covers.
  - Numbers kept: 5-minute dedupe, 90-day retention, 2,000 rows per member per day, 500 queued
    on the TV.
- Grill round 2 (2026-10-14), all on the recommended answer:
  - Testing: local database copy and emulator during the build; the hosted migration and the
    kevbox.dev deploy only on Kevin's word at the end, then the TCL 403 check. Rejected: testing
    against the hosted database during the build.
  - A member's TVs show as model plus a 4-character device tag. Rejected: model only, which
    can't tell two TCLs apart.
  - Needs Attention stays unchanged. Rejected: flagging expired or banned accounts there now.
  - Live errors rows link to the customer window. Rejected: no link.
- auto-resolved: the reporter watches `LivePreviewEngine.errorInfo` as well as
  `OwnTVPlayer.errorInfo` (AC-10, AC-21), because KevBox Live plays live channels on
  `LivePreviewEngine` in both the top box and full screen; `OwnTVPlayer` plays only catch-up and
  mpv handovers.
- auto-resolved: the error name comes from `ErrorInfo.raw` text (AC-10, AC-11), because
  `ErrorInfo` holds `reason`, `spec` and a `raw` string, not the `PlaybackException`, and Core
  exposes no hook for the exception. `PlayerErrors.httpStatusOf` takes a `Throwable`, so the
  reporter uses `httpStatusIn` on `raw` instead.
- auto-resolved: `preview` or `full` comes from where the Live video window sits
  (`VideoSite.BOX` is `preview`, anything else `full`), because one engine serves the box, full
  screen and the mini-player. `OwnTVPlayer` failures are always `full`.
- auto-resolved: Multiview tile engines (`LiveEnginePool`) and the Home hero preview are not
  watched. They are separate engines, and AC-10 gives them no `preview`/`full` value.
- auto-resolved: playlist failures come from `SourceRepository.getLastSyncStats` once
  `CatalogSyncScheduler.observeSync` goes idle, plus the account check (AC-12, AC-13), because
  `CatalogSyncState` carries no failure and `SyncResult.Failed` holds only a message.
- auto-resolved: guide failures come from `EpgSource.lastError` (AC-14), because Core writes
  guide failures there (`EpgSourceStore.markError`) and `EpgSyncState` carries none.
- auto-resolved: the account check calls Core's `XtreamClient.fetchAccountStatus(source)` on the
  TV, which sends the playlist's user agent through Core's HTTP client and global proxy. The
  credentials never leave the TV; only `status`, `active_cons` and `max_connections` do. Rejected:
  a check from kevbox.dev, which comes from a different IP and needs the credentials there.
- auto-resolved: proxy on or off reads Core's global proxy setting
  (`SettingsRepository.proxyConfig`), because `ManagedProxy` writes kevbox.dev's proxy there and
  every stream uses it.
- auto-resolved: debug builds never send to Sentry. `app/build.gradle.kts` sets the DSN build
  field only on the `release` build type; debug gets a blank one, so the AC-4 no-key path runs.
- auto-resolved: Sentry auto-init is off. `OwnTVApp.onCreate` starts Sentry by hand right after
  `CrashRecorder.install`, so a keyless build never touches Sentry (AC-4) and Sentry's handler
  hands each crash on to `CrashRecorder`'s (AC-8).
- auto-resolved: Sentry environment `production` (only release builds send), release
  `tv.kevbox.live@<versionName>+<versionCode>` (the SDK default, from `release.sh`'s
  `VERSION_NAME` and `VERSION_CODE`), project slug `kevbox-live`.
- auto-resolved: the Sentry values, including the Gradle plugin's org and project slugs, go in
  `~/secrets/kevbox-keys/kevbox-live.env`, the file `release.sh` already reads for Supabase
  (AC-35). Rejected: a second secrets file.
- auto-resolved: native symbols (AC-9). Core's libmpv, ffmpeg and libplayer `.so` files ship
  stripped (checked in libmpv 2026.10.3, arm64-v8a), so the upload gives native frames a library
  and offset, not full function names. Fixing that needs Core's unstripped builds, which Core
  does not publish.
- auto-resolved: device id is a random UUID the reporter makes on first run and keeps in a private
  prefs file, because KevBox Live sends no device id to Supabase today. Rejected: `ANDROID_ID`,
  which the app never reads. The AC-31 tag is its last 4 characters.
- auto-resolved: the reporter lives in `app/src/main/java/tv/own/owntv/kevbox/errors/`. It sends
  through a new `SupabaseApi` call to `rest/v1/rpc/record_live_errors` (direct, never through the
  member's proxy) with `KevBoxAuth`'s fresh token, and `KevBoxAuth` exposes the signed-in user id
  it already stores, for Sentry (AC-1).
- auto-resolved: the next migration is `0015`. kevbox `main` ends at
  `0014_member_playlist_proxy.sql`, and no branch holds a `0015`.
- auto-resolved: a customer's errors list shows every error of the customer's login (the user id
  `findLoginId` finds from the sheet's Stremio email), because `live_error` has no client number.
  A login with several playlists shows the same list in each customer window.
- auto-resolved: a Live errors row links to `/customers?highlight=<client number>` for each
  `member_playlist` client number of the row's user id. Today that address only scrolls to and
  flashes the row, so the build makes it open the window (AC-32).
- auto-resolved: admin routes follow `src/app/api/activity/stats/route.ts` (`requireOperator`,
  `getAdminPool`, `shapeError`), with the queries in `packages/core/src`:
  `GET /api/live-errors?range=24h|7d`, `GET /api/live-errors/rows?code=<code>&range=<range>` and
  `GET /api/members/[userId]/live-errors` (AC-34).
- Grill: run to an empty frontier
- Size: 35 criteria, within the cap

## Open questions

## UI

- **Platform:** web, kevbox.dev only (Next.js admin). The TV app's screens don't change (AC-22).
- **Look:** kevbox.dev's existing admin design system (its shadcn components in
  `src/components/ui/`, the same tables, tabs and badges the customer window and Fleet page use).
  No new visual direction.
- **21st:** no. Both views are tables and lists inside existing pages.
