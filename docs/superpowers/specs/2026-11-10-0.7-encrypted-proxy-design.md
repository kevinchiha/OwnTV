# 0.7-encrypted-proxy: design

## Goal

A KevBox Live customer with the VPS proxy switched on reaches persovps over an encrypted (TLS)
connection on port 443 of persovps's second address, so an internet company that inspects their
traffic sees ordinary HTTPS: not the provider's address, not the channel links (which carry the
customer's IPTV login), not the proxy password. The customer sees nothing new.

## Scope

- **Builds on 0.6, which is released** (app v5.2.1.7, migration 0023 live on KevBox Supabase).
  Both bases already hold it: `kevbox-live` (OwnTV) and `main` (kevbox). 0.7 uses 0.6's Realtime
  subscription, its automatic channel restart (0.6 AC-40), its VPN either/or (0.6 AC-25) and its
  playlist column fallback (0.6 AC-23).
- **persovps (server; applying any change is gated).** Already done: the second public address
  `45.146.255.87` on `eth0`, kept across reboots by `/etc/systemd/system/kevbox-second-ip.service`;
  the domain `northcache.uk` with one DNS A record to `45.146.255.87` and a CAA record allowing
  only Let's Encrypt. Still to write: nginx's `listen 443` lines pinned to `185.223.31.163`;
  Debian's `squid-openssl` build in place of the GnuTLS one; Squid's TLS port
  `https_port 45.146.255.87:443` beside `http_port 38129`, same login file and rules, Squid's name
  and version hidden, `45.146.255.87` added to the blocked destinations; a Let's Encrypt
  certificate for `northcache.uk` renewed by certbot with a hook that reloads Squid; the
  `squid-auth` fail2ban jail on port 443 of `45.146.255.87` too. All of it is written in the kevbox repo as
  config files and a runbook under `deploy/squid-tls/`.
- **kevbox (kevbox.dev, base `main`).** Migration `0024_live_proxy_tls.sql` (three columns on
  `member_playlist`) and the same three columns in `packages/core/test/schema.sql`. The proxy
  writes fill or clear them from new environment settings: `src/server/admin/live-proxy.ts`
  (`liveProxyFields`, `vpsProxyChoice`, `writeVpsProxyToLive`), `src/server/admin/live.ts`
  (`updateLiveProxy`, `getLiveRow`), `src/lib/vps-proxy.ts` (`vpsProxyEndpoint`),
  `src/app/live-actions.ts` (`setKevboxLiveProxy`, `sendToKevboxLive`), `src/app/actions.ts`
  (delete and client-number change). `packages/core/src/liveVpn.ts` `turnLiveVpnOn` clears them.
  The 15-minute refresh (`scripts/refresh-vps-proxy-access.ts`) keeps them in line with the
  client-number list. The customer window marks encrypted TVs, with the first relay version as a
  constant in `packages/core/src/liveVersion.ts`.
- **OwnTV app (`kevbox/` layer, base `kevbox-live`).** A local relay in `kevbox/network/` that
  listens on 127.0.0.1 and wraps each connection in TLS to persovps. `ManagedProxy` points Core's
  proxy at the relay when the playlist carries an encrypted address, and the relay starts at app
  start from the last applied address. `SupabaseApi` and `KevBoxModels` read the new columns, with
  one more fallback step for a server without 0024. The silent self-update (`kevbox/release/`
  `SilentUpdater`) moves to a direct HTTP client. Wiring in `KevBoxCoordinator` and
  `di/KevBoxModule.kt`.

## How it works

1. Kevin switches the VPS proxy on in the customer window, as today. kevbox.dev writes the plain
   address (`proxy_host`, `proxy_port`) for app versions without the relay, and, for a client
   number on `VPS_PROXY_TLS_CLIENTS`, the encrypted address (`proxy_tls_host`, `proxy_tls_port`,
   `proxy_tls_addr`) beside it.
2. The TV hears of it within seconds through 0.6's Realtime subscription. A version with the
   relay starts it on 127.0.0.1 and saves Core's proxy as `127.0.0.1:<relay port>` with the same
   `kb<clientNumber>` login. ExoPlayer, mpv, the guide and the logos all use Core's one proxy
   setting, so all of them go through the relay.
3. For each connection a player opens to the relay, the relay opens one TLS connection to
   `45.146.255.87:443` (no DNS lookup), sends `northcache.uk` as the server name, checks the
   certificate, and copies bytes both ways unchanged. The proxy request, login included, travels
   inside the TLS.
4. Squid on `45.146.255.87:443` takes off the TLS and handles the request exactly like one on
   38129: same login file, same On / not cancelled / not expired rule, same blocked destinations.
5. Old app versions keep using `185.223.31.163:38129` in the clear until the silent self-update
   moves them. 38129 closes later, at Kevin's word.

An internet company then sees a TLS connection to `45.146.255.87:443`, the name `northcache.uk` in
its first message, and the volume and timing of the traffic.

## Acceptance criteria

### persovps: second address and encrypted port

- **AC-1** `45.146.255.87` answers on persovps beside `185.223.31.163`, and still does after a
  reboot from inside the server. What holds it is `kevbox-second-ip.service` (already applied),
  not `/etc/network/interfaces.d/50-cloud-init`, which cloud-init rewrites. The reboot check runs
  once the rest of the runbook is applied.
- **AC-2** Every nginx `listen 443` line names `185.223.31.163`; the IPv6 lines stay as they are.
  Before and after the change, each of the 11 sites in `/etc/nginx/sites-enabled` answers on
  `https://<its name>/` with the same status code, and the catch-all still closes unknown names.
  Port 80 is unchanged.
- **AC-3** Squid listens with TLS on `45.146.255.87:443` and keeps `http_port 38129`. Through the
  TLS port, a request with an On `kb<clientNumber>` login gets the destination's answer; a wrong
  password gets Squid's 407; a destination in the blocked list (now including `45.146.255.87`)
  gets 403. A plain-text connection to the TLS port gets no proxy answer.
- **AC-4** Squid on persovps is Debian's `squid-openssl` build (`squid -v` shows `--with-openssl`).
  The TLS port accepts TLS 1.2 and 1.3 and refuses 1.0 and 1.1 (`tls-min-version=1.2` on the
  port). It presents the Let's Encrypt certificate for `northcache.uk` with its full chain, the
  leaf and its intermediate, so a client holding only the roots (as Android does) verifies it; the
  chain ends at ISRG Root X1 (certbot `--preferred-chain "ISRG Root X1"`).
  `certbot renew --dry-run` passes, and a renewal reloads Squid through a deploy hook, so the new
  certificate is in use without a manual step.
- **AC-5** The `squid-auth` jail bans on the TLS port as well as 38129: 10 wrong passwords in 10
  minutes over TLS ban the address for 1 hour, as today. The ban on port 443 covers destination
  `45.146.255.87` only, so a banned address still reaches every website on `185.223.31.163:443`;
  the ban on 38129 stays as today.
- **AC-6** Squid's access log records the customer's real address for TLS connections, as it does
  for 38129.
- **AC-28** Squid's answers carry neither its name nor its version: `httpd_suppress_version_string
  on`, and error pages with no Squid branding, on both ports.
- **AC-7** Every server change is a file in `deploy/squid-tls/` in the kevbox repo, plus a runbook
  that lists the steps in order, each with its check and its undo. The files start from
  persovps's current config, read over SSH without changing anything. `kevbox-second-ip.service`
  is copied in and its step marked done. The runbook warns that a site added later with
  `certbot --nginx` gets an unpinned `listen 443`, which stops nginx from starting while Squid
  holds `45.146.255.87:443`, and states the rule for closing 38129 (Decisions). Nothing is
  applied to persovps without Kevin's go-ahead at the time.

### kevbox.dev

- **AC-8** Migration `0024_live_proxy_tls.sql` adds `proxy_tls_host text`, `proxy_tls_port int`
  and `proxy_tls_addr text` (the proxy's IPv4 address) to `member_playlist`, and
  `packages/core/test/schema.sql` carries the same three columns. Host and port both null means no
  encrypted address. Members read them on their own rows under the existing lock rule (0013), and
  nothing while locked.
- **AC-9** When kevbox.dev writes a proxy that is on for a customer whose client number is on
  `VPS_PROXY_TLS_CLIENTS` (comma-separated client numbers, or `all`; empty or missing means
  nobody), it also writes `proxy_tls_host`, `proxy_tls_port` and `proxy_tls_addr` from
  `VPS_PROXY_TLS_HOST`, `VPS_PROXY_TLS_PORT` and `VPS_PROXY_TLS_ADDR` in `/etc/kevbox-www/env`
  (`northcache.uk`, `443`, `45.146.255.87`). `VPS_PROXY_TLS_ADDR` is optional: missing or not a
  valid IPv4 address writes `proxy_tls_addr` as null. For a customer not on the list, or when the
  host or port setting is missing or invalid, it writes all three as null and the plain proxy
  works as today. Switching the proxy off clears all three, the same way it clears the plain
  fields.
- **AC-26** The 15-minute refresh (`scripts/refresh-vps-proxy-access.ts`) also brings every
  `member_playlist` row whose proxy is on into line with AC-9: it fills the encrypted address for
  customers on the list and clears it for customers off it. It writes only rows whose three values
  differ from what AC-9 gives, so an unchanged row is never rewritten and its TV gets no Realtime
  change. Removing a client number from the list, or emptying it, moves that TV back to the plain
  proxy within one refresh. A failure in this step does not stop the other steps, and makes the
  run exit 1.
- **AC-10** Every place that writes the proxy fields of `member_playlist` today writes the
  encrypted address by the same rule as AC-9: the switch (`setKevboxLiveProxy` →
  `writeVpsProxyToLive`), Send to KevBox Live (`sendToKevboxLive`), and the delete and
  client-number-change paths in `src/app/actions.ts`. Turning the VPN on (`turnLiveVpnOn`) clears
  the encrypted address with the plain one. 0.6's either/or with the VPN is unchanged.
- **AC-11** The customer window shows the same VPS proxy switch with no new control.
- **AC-29** In the customer window's KevBox Live box, a TV's watch status line ends in
  " · encrypted" when that customer's row carries an encrypted address and the TV's last reported
  app version is at or above `RELAY_MIN_VERSION` in `packages/core/src/liveVersion.ts`. It shows
  nothing new otherwise: an older app, an unknown version, or a row without an encrypted address.
  The TV reports nothing new for this.

### OwnTV app

- **AC-12** The playlist read asks for `proxy_tls_host`, `proxy_tls_port` and `proxy_tls_addr`
  with the proxy and VPN columns. A server without 0024 refuses them; the app then asks without
  them and reads the proxy as plain, the same fallback pattern as 0.6's AC-23.
- **AC-13** When the visible playlist's proxy is on and carries a valid encrypted address
  (non-blank host, port 1-65535), the app runs the relay and saves Core's proxy as
  `127.0.0.1:<relay port>` with the playlist's proxy login. The plain `proxy_host` is never saved
  into Core's setting in this case.
- **AC-14** The relay listens on 127.0.0.1 only, so other devices on the home network cannot use
  it.
- **AC-15** For each accepted connection, the relay opens a TLS connection to
  `proxy_tls_addr:proxy_tls_port` with no DNS lookup, or, when `proxy_tls_addr` is null or not a
  valid IPv4 address, to `proxy_tls_host:proxy_tls_port` through DNS. Either way it sends
  `proxy_tls_host` as the server name, and checks the certificate and the host name against the
  same roots Core trusts: Android's own plus Core's bundled Let's Encrypt roots
  (`tv.own.owntv.core.network.ExtraTrustAnchors`, `res/raw/isrg_extra_roots.pem` in Core 1.0.69).
  It then copies bytes both ways unchanged, and closing either side closes the other.
- **AC-16** A certificate that fails the check, or a TLS connection that fails, closes the
  player's connection. The relay never falls back to the plain port or to a direct connection.
- **AC-17** The relay's port stays the same for the life of the app process, so coming back to
  the app or a playlist re-check does not rewrite Core's setting and restart the channel. The
  relay tries port 61129 first and takes a free one only when that is busy.
- **AC-25** The TV keeps the last encrypted address it applied, beside Core's saved proxy. When
  the app process starts (opening the app, or `HomeRowsBootReceiver`'s job at boot), the relay
  starts from that address before any playlist fetch, so Core's saved `127.0.0.1` setting never
  points at a dead port while kevbox.dev is unreachable. If the relay has to take a different
  port, it updates Core's setting at once. Applying a proxy without an encrypted address, the
  proxy switched off, the VPN taking over and sign-out all clear the kept address.
- **AC-18** A proxy with no encrypted address (server without 0024, settings missing, client
  number not on the list) is applied as a plain proxy, exactly as today.
- **AC-19** When the encrypted address appears, disappears or changes through Realtime while a
  channel plays, Core's proxy and the relay's target are updated and the channel restarts by
  itself, by 0.6's AC-40 rule. A change to the encrypted host, port or address alone counts as a
  change, even though Core's saved `127.0.0.1:<port>` stays the same.
- **AC-20** The relay stops when the proxy is switched off, when the VPN takes over (0.6 AC-25),
  and on sign-out.
- **AC-21** KevBox's own server calls (`SupabaseApi`, `NO_PROXY`) never go through the relay.
- **AC-27** The silent self-update (`SilentUpdater` in `kevbox/release/`: the version check and
  the APK download) goes straight to the internet with no proxy and no relay, the same way
  `SupabaseApi` does, instead of through Core's shared HTTP client, which follows Core's proxy
  setting. A relay that fails closed (AC-16) then never blocks the update that fixes it.
- **AC-22** ExoPlayer plays a channel through the relay, checked on the `kevbox_tv` emulator against a local TLS proxy. (Amended 2026-11-10 at Kevin's word: mpv is out of scope, see Decisions.)
- **AC-23** The "proxy in use" flag in error reports and play notes (`ProxyInUse`) reads true when
  the relay carries the traffic, as it does for the plain proxy.
- **AC-24** Nothing new appears on the TV screen. The app's own Proxy screen stays hidden.

## Non-goals

- **WireGuard or any other VPN on persovps.** Decided before this phase: it looks like a VPN,
  needs a key per customer, and fights the Premiumize VPN for Android's one VPN slot.
- **Changes to the Premiumize VPN.** It stays as 0.6 built it, either/or with the proxy.
- **Changes to the Squid logins or who may use the proxy.** Same `kb<clientNumber>` logins, same
  login file, same 15-minute refresh of the login file.
- **The provider's 407 answers on reconnect.** They come from the provider, not Squid, and have
  nothing to do with TLS.
- **Hiding the proxy's name in the first message (Encrypted Client Hello).** Neither Squid nor
  Android's TLS supports it in a usable way today.
- **Closing port 38129 inside this phase.** It stays open until every proxy customer's TV runs a
  version with the relay; Kevin closes it later.
- **A second proxy server.** Moving load off persovps is the Premiumize VPN's job.
- **Cloudflare in front of the proxy or the websites.** Its terms forbid serving video through its
  CDN without its paid video products, a raw proxy needs its paid TCP product (Spectrum), every
  stream would pass through a company that acts on anti-piracy complaints, and in Spain LaLiga's
  court order has the big internet companies block Cloudflare addresses during matches (in force
  at the start of the 2026-27 season). Cloudflare for the websites alone is a separate idea for
  later.
- **Hiding from someone who probes the port.** A stranger who connects to `45.146.255.87:443`
  without a login gets Squid's "proxy login required" answer, so they can tell a proxy is there.
  Hiding that needs a different front program, which breaks "the same Squid", and the internet
  companies in question block by address and name rather than probing. AC-28 removes Squid's name
  and version only.
- **Taking Core's own "Update now" path off the proxy.** Core's updater and the profile download
  that rides on it (`UpdateProfileAttacher`) use Core's shared client; changing that means
  changing Core. The silent self-update (AC-27) is the path that always gets through.

## Decisions

- Size: 29 criteria, within the cap
- Grill: run to an empty frontier
- **Approach C: a second address, the proxy alone on its port 443**, over A (a separate port such
  as 8443 on the current address) and B (port 443 shared with the websites by name through
  nginx's stream module). C gives port 443 without rebuilding how the 11 websites get traffic,
  and blocking the proxy's address does not block kevbox.dev. A uses an unusual port; B touches
  every live website, tv.kevbox.dev's app updates included.
- **A local relay in the app**, over teaching the players to speak to an encrypted proxy. OkHttp
  (ExoPlayer's network library) and mpv only speak plain HTTP proxies.
- **Squid handles the TLS itself (`https_port`)**, over stunnel or nginx in front of 38129. Squid
  then still sees each customer's real address, so its log and the fail2ban jail keep working.
  (My call.)
- **persovps moves to Debian's `squid-openssl` build** (decided at gap fold), over keeping the
  GnuTLS build it runs today (`6.13-2+deb13u4`). Tested 2026-11-10 in throwaway `debian:trixie`
  containers with Squid 6.13. The GnuTLS build sends only the leaf from `tls-cert=fullchain.pem`,
  never the intermediate (`tls-cafile` changes nothing), so Android, which never fetches a missing
  intermediate, and curl both refuse a Let's Encrypt certificate; on top of that
  `tls-min-version=1.2` makes it exit at start and `tls-options=NORMAL:-VERS-TLS1.0:-VERS-TLS1.1`
  makes the port refuse every client. `apt install squid-openssl` installs beside `squid`, and
  Debian's alternatives point `/usr/sbin/squid`, which `squid.service` runs, at
  `/usr/sbin/squid-openssl`, so a restart picks it up; `/etc/squid/squid.conf` is untouched and
  `squid -v` shows `--with-openssl`. With a root → intermediate → leaf test chain it sent both
  certificates (verify code 0), `tls-min-version=1.2` refused TLS 1.0 and 1.1 while 1.2 and 1.3
  worked, a good login got 200 and a wrong password 407. Undo: `update-alternatives --set squid
  /usr/sbin/squid-gnutls` (or remove `squid-openssl`) and restart Squid.
- **The fail2ban ban on port 443 matches destination `45.146.255.87` only** (decided at gap fold),
  through a custom nftables action beside the stock 38129 ban, over `port = 38129,443` on the stock
  action. The stock nftables action matches source and port on every address of the server, so it
  would ban the address from all 11 websites on `185.223.31.163:443` (kevbox.dev, tv.kevbox.dev's
  app updates, KevBox TV's sites) for the hour, for every device in that household, and an expired
  customer's TV still sending its old login is exactly what sets a ban off. Approach C exists so
  that blocking the proxy does not block the websites.
- **The relay starts at app start from the last applied address** (AC-25), over starting it only
  after a playlist fetch, which would point every request at a dead `127.0.0.1` port while
  kevbox.dev is unreachable and make the start-up provider check (`ExpiryMonitor`) send false
  error reports. The TV already keeps the proxy password in Core's settings. (My call.)
- **The build reads persovps's config over SSH, read-only**, to start the `deploy/squid-tls/`
  files from what is there (AC-7), over Kevin pasting it in. (My call.)
- **New columns for the encrypted address**, over reusing `proxy_host` and `proxy_port`. Old app
  versions read those two and must keep getting the plain address until they update.
- **A Let's Encrypt certificate checked against Android's roots**, over a self-signed one pinned
  in the app. It looks like any website's certificate to an observer, certbot already runs on
  persovps, and the app's minimum Android (8.0) trusts Let's Encrypt's root. (My call.) Neither
  Android nor Core's bundled roots hold Let's Encrypt's intermediates, so Squid must send the
  intermediate with the leaf, which the `squid-openssl` build does.
- **The second address `45.146.255.87`** (ZAP-Hosting, `45.146.252.0/22`) is held by
  `kevbox-second-ip.service`, a systemd oneshot running `ip addr replace 45.146.255.87/32 dev
  eth0`, ordered after `networking.service` and before `network-online.target`, `squid.service`
  and `nginx.service`, enabled for `multi-user.target`; applied with Kevin's go-ahead on
  2026-11-10, undo in its header. Chosen over a second `iface eth0` stanza because `replace`
  succeeds whether or not ZAP's panel already added the address (a panel start adds it through
  the QEMU guest agent; a reboot from inside does not), and the ordering puts it in place before
  Squid binds. Replies leave through `185.223.31.1`; no gateway of its own.
- **Customers move over through the 15-minute refresh and a client-number list** (AC-9, AC-26),
  over a one-off fill script (all at once, undone by another script) and over Kevin flipping each
  customer (manual, error-prone). `VPS_PROXY_TLS_CLIENTS` starts with Kevin's client number only.
  One list is the rollout plan, the fill for customers already on, and the off switch: emptying
  it puts every TV back on the plain proxy within 15 minutes. The refresh reads the env file fresh
  on every run, but the web app (`kevbox.service`) reads it only when it starts, so every edit of
  the `VPS_PROXY_TLS_*` lines is followed by `sudo systemctl restart kevbox.service`; otherwise the
  switch and Send keep writing by the old list and flip a TV back and forth against the refresh.
  The refresh's proxy step starts writing `member_playlist`; until now only its VPN step (0.6) did.
- **The encrypted path fails closed, and the self-update skips the proxy** (AC-16, AC-27), over
  falling back to the plain port. A fallback would hand an inspecting internet company exactly
  what 0.7 hides, and 38129 could never close. Internet companies block the IPTV provider, not
  GitHub, so a direct self-update reaches these TVs. Kevin hears of failures through the existing
  "can't watch" Telegram ping.
- **Squid's name and version are hidden; probing is accepted** (AC-28, Non-goals).
- **0.6 released on its own first; 0.7 is a later release**, over one release for both: a fault
  then points at one phase. Done: 0.6 shipped as v5.2.1.7.
- **Kevin's customer window marks encrypted TVs** (AC-29), worked out from the row and the TV's
  reported app version, with no new reporting from the TV. The same data later shows when every
  proxy customer has updated.
- **The proxy uses a separate, plain-looking domain bought for it alone**, over a `kevbox.dev`
  subdomain. The name travels in the clear; a kevbox.dev name leads to tv.kevbox.dev, which hands
  out `KevBoxLive.apk`, and public certificate logs would list it beside the other kevbox.dev
  names. A name-based block on one domain then never takes down the other, and a burned name is
  replaced through `VPS_PROXY_TLS_HOST` with no app release. Auto-renew and the registrar's owner
  privacy are on.
- **The domain is `northcache.uk`**, bought by Kevin at Namecheap on 2026-11-10, over the
  $1-first-year extensions (`.xyz`, `.site`, `.online`, `.ink`), which renew at about $19-39 a
  year and carry spam reputations that get whole extensions blocked; `.uk` renews at about $10.
  DNS: one A record to `45.146.255.87` and a CAA record allowing only `letsencrypt.org`, both set.
- **The TV connects to the proxy by address, with no DNS lookup** (AC-15), over looking the name
  up. DNS blocking (the usual tool of French IPTV court orders, and of router and "safe browsing"
  filters) then cannot touch the proxy; the name is used only for the server name and the
  certificate check. A changed address reaches TVs through `VPS_PROXY_TLS_ADDR` and the 15-minute
  refresh.
- **38129 closes at Kevin's word once every customer whose proxy is on has shown "encrypted"
  (AC-29) for 7 days in a row.** The runbook says so; closing it (Squid's `http_port 38129` and
  its ufw rule) is not part of 0.7's build.
- **Cloudflare stays out of 0.7** (Non-goals).
- auto-resolved: the relay's first-choice port is 61129 (AC-17), over leaving the number to the
  plan, because a named value is testable and 61129 sits above Linux's outgoing-connection range
  (32768-60999), so the system rarely hands it to something else.
- auto-resolved: sign-out, the proxy switched off, the VPN taking over, and a proxy applied
  without an encrypted address all clear the kept encrypted address (AC-25), over keeping it until
  the next one arrives, because a stale kept address would start a relay at the next app start
  for a TV that should have no relay.
- auto-resolved: the app treats a `proxy_tls_addr` that is not a valid IPv4 address as null and
  looks the host up (AC-15), over refusing the encrypted address, because kevbox.dev already
  writes null for an invalid address and a DNS lookup still keeps the traffic encrypted.
- auto-resolved: `VPS_PROXY_TLS_HOST` and `VPS_PROXY_TLS_PORT` are checked like
  `vpsProxyEndpoint` checks the plain ones (trimmed host not blank; port all digits, 1-65535),
  over a stricter host-name check, because the setting is Kevin's own and the TV's certificate
  check refuses a wrong name anyway.
- auto-resolved: `VPS_PROXY_TLS_CLIENTS` entries are trimmed and empty entries ignored; a client
  number matches only exactly; the whole value `all`, in any letter case, means everyone. Rejected:
  `all` as one entry among numbers, because a mixed list is more likely a typo than a choice.
- auto-resolved: the refresh treats a row as the VPS proxy only when its `proxy_host` and
  `proxy_port` equal `VPS_PROXY_HOST` and `VPS_PROXY_PORT`, and clears the encrypted address on
  any other proxy-on row (AC-26), over filling every proxy-on row, because an encrypted address to
  persovps beside some other proxy would send that TV somewhere Kevin did not choose.
- auto-resolved: the refresh's encrypted-address work runs as its own step under the script's
  existing rule (each step runs even when another fails; exit 1 when any did), over folding it
  into the Squid-file step, because a database fault must not stop the login file being rebuilt.
- auto-resolved: "encrypted" appears on the TV's line in the KevBox Live box's watch list
  (`KevboxLiveWatch`, `src/components/kevbox-live-watch.tsx`); the customer summary boxes, which
  reuse `watchStatusLine`, stay unchanged (AC-29), over adding it everywhere that function shows,
  because the grill placed it in the KevBox Live box only.
- auto-resolved: `RELAY_MIN_VERSION` is set by the build to the version 0.7 is planned to ship as,
  and the release step checks it matches before kevbox.dev deploys, over waiting until release
  day to write it; a value set too high only hides the word, the safe side. The release step reads
  the kevbox checkout at `~/projects/kevbox`, so 0.7's kevbox code is in that checkout before the
  release, and a `liveVersion.ts` there without the `RELAY_MIN_VERSION` line refuses the release
