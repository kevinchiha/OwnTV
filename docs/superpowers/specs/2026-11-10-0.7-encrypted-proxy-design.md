# 0.7-encrypted-proxy: design

## Goal

A KevBox Live customer with the VPS proxy switched on reaches persovps over an encrypted (TLS)
connection on port 443 of persovps's second address, so an internet company that inspects their
traffic sees ordinary HTTPS. It no longer sees the provider's address, the channel links (which
carry the customer's IPTV login) or the proxy password. The customer sees nothing new.

## Scope

- **persovps (server, every change gated):** the second public address `45.146.255.87` set up on
  `eth0` and kept across reboots. nginx's `listen 443` lines pinned to `185.223.31.163` so port
  443 on the new address is free. Squid gets a TLS port, `https_port 45.146.255.87:443`, with the
  same login file and rules as today's `http_port 38129`. A Let's Encrypt certificate for the
  proxy's name, renewed by certbot with a hook that reloads Squid. The `squid-auth` fail2ban jail
  covers port 443 too. These changes are written in the kevbox repo as config files and a runbook
  (`deploy/squid-tls/`); applying them waits for Kevin each time.
- **kevbox (kevbox.dev, branch base `main`):** migration `0024_live_proxy_tls.sql`, which adds the
  encrypted address to `member_playlist`. The writes in `src/server/admin/live.ts` and
  `src/lib/vps-proxy.ts` (`vpsProxyEndpoint`) fill it from new environment settings. Functions
  copied to `packages/core/test/schema.sql` as with 0023.
- **OwnTV app (`kevbox/` layer, branch base `kevbox-live`):** a local relay in
  `kevbox/network/` that listens on 127.0.0.1 and wraps each connection in TLS to persovps.
  `ManagedProxy` points Core's proxy at the relay when the playlist carries an encrypted address.
  `SupabaseApi` and `KevBoxModels` read the new columns, with one more fallback step for a server
  without 0024. Wiring in `KevBoxCoordinator` and `di/KevBoxModule`.

## How it works

1. Kevin switches the VPS proxy on in the customer window, exactly as today. kevbox.dev writes
   the plain address (`proxy_host`, `proxy_port`) as before, for app versions without the relay,
   and the encrypted address (`proxy_tls_host`, `proxy_tls_port`) beside it.
2. The TV hears of it within seconds through 0.6's Realtime subscription. A version with the
   relay starts it on 127.0.0.1 and saves Core's proxy as `127.0.0.1:<relay port>` with the same
   `kb<clientNumber>` login. ExoPlayer, mpv, the guide and the logos all use Core's one proxy
   setting, so all of them go through the relay.
3. For each connection a player opens to the relay, the relay opens one TLS connection to
   `proxy_tls_host:443`, sends the proxy's name, checks the certificate, and copies bytes both
   ways unchanged. The player's proxy request, login included, travels inside the TLS.
4. Squid on `45.146.255.87:443` takes off the TLS and handles the request exactly like one on
   38129: same login file, same On / not cancelled / not expired rule, same blocked
   destinations.
5. Old app versions keep using `185.223.31.163:38129` in the clear until they update through the
   silent self-update. 38129 closes later, at Kevin's word.

What an internet company sees: a TLS connection to `45.146.255.87:443`, the proxy's name in its
first message, and the volume and timing of the traffic. No address of the provider, no link,
no login.

## Acceptance criteria

### persovps: second address and encrypted port

- **AC-1** `45.146.255.87` answers on persovps beside `185.223.31.163`, and still does after a
  reboot. Its config lives in a file that cloud-init (the tool that rewrites
  `/etc/network/interfaces.d/50-cloud-init` from the host's data) does not overwrite.
- **AC-2** Every nginx `listen 443` line names `185.223.31.163`; the IPv6 lines stay as they are.
  Before and after the change, each of the 11 sites in `/etc/nginx/sites-enabled` answers on
  `https://<its name>/` with the same status code, and the catch-all still closes unknown names.
  Port 80 is unchanged.
- **AC-3** Squid listens with TLS on `45.146.255.87:443` and keeps `http_port 38129`. Through the
  TLS port, a request with an On `kb<clientNumber>` login gets the destination's answer; a wrong
  password gets Squid's 407; a destination in the blocked list (now including `45.146.255.87`)
  gets 403. A plain-text connection to the TLS port gets no proxy answer.
- **AC-4** The TLS port offers TLS 1.2 and 1.3 only, with the Let's Encrypt certificate for the
  proxy's name. `certbot renew --dry-run` passes, and a renewal reloads Squid through a deploy
  hook, so the new certificate is in use without a manual step.
- **AC-5** The `squid-auth` jail bans on port 443 as well as 38129: 10 wrong passwords in 10
  minutes over TLS ban the address for 1 hour, as today.
- **AC-6** Squid's access log records the customer's real address for TLS connections, as it does
  for 38129.
- **AC-7** The build writes every server change as a file in `deploy/squid-tls/` plus a runbook
  that lists the steps in order, each with its check and its undo. Nothing is applied to persovps
  without Kevin's go-ahead at the time.

### kevbox.dev

- **AC-8** Migration `0024_live_proxy_tls.sql` adds `proxy_tls_host text` and
  `proxy_tls_port int` to `member_playlist`. Both null means no encrypted address. Members read
  them on their own rows under the existing lock rule (0013), and nothing while locked.
- **AC-9** When kevbox.dev writes a proxy that is on, it also writes `proxy_tls_host` and
  `proxy_tls_port` from `VPS_PROXY_TLS_HOST` and `VPS_PROXY_TLS_PORT` in `/etc/kevbox-www/env`.
  If either setting is missing or invalid, it writes both as null and the plain proxy works as
  today. Switching the proxy off clears both, the same way it clears the plain fields.
- **AC-10** Every place that writes the proxy today (the switch, Send to KevBox Live, Edit, the
  15-minute refresh, renew, cancel and uncancel, delete) writes the encrypted address by the same
  rule as AC-9. 0.6's either/or with the VPN is unchanged.
- **AC-11** The customer window shows the same VPS proxy switch with no new control.

### OwnTV app

- **AC-12** The playlist read asks for `proxy_tls_host` and `proxy_tls_port` with the proxy
  columns. A server without 0024 refuses them; the app then asks without them and reads the
  proxy as plain, the same fallback pattern as 0.6's AC-23.
- **AC-13** When the visible playlist's proxy is on and carries a valid encrypted address
  (non-blank host, port 1-65535), the app runs the relay and saves Core's proxy as
  `127.0.0.1:<relay port>` with the playlist's proxy login. The plain `proxy_host` is never saved
  into Core's setting in this case.
- **AC-14** The relay listens on 127.0.0.1 only, so other devices on the home network cannot use
  it.
- **AC-15** For each accepted connection, the relay opens a TLS connection to
  `proxy_tls_host:proxy_tls_port`, sends the host as the server name, and checks the certificate
  against Android's trusted roots and the host name. It then copies bytes both ways unchanged,
  and closing either side closes the other.
- **AC-16** A certificate that fails the check, or a TLS connection that fails, closes the
  player's connection. The relay never falls back to the plain port or to a direct connection.
- **AC-17** The relay's port stays the same for the life of the app process, so coming back to
  the app or a playlist re-check does not rewrite Core's setting and restart the channel.
- **AC-18** A proxy with no encrypted address (server without 0024, settings missing) is applied
  as a plain proxy, exactly as today.
- **AC-19** When the encrypted address appears, disappears or changes through Realtime while a
  channel plays, Core's proxy is updated and the channel restarts by itself, by 0.6's AC-40 rule.
- **AC-20** The relay stops when the proxy is switched off, when the VPN takes over (0.6 AC-25),
  and on sign-out.
- **AC-21** KevBox's own server calls (`SupabaseApi`, `NO_PROXY`) never go through the relay.
- **AC-22** ExoPlayer and mpv both play a channel through the relay, checked on the `kevbox_tv`
  emulator against a local TLS proxy.
- **AC-23** The "proxy in use" flag in error reports and play notes (`ProxyInUse`) reads true when
  the relay carries the traffic, as it does for the plain proxy.
- **AC-24** Nothing new appears on the TV screen. The app's own Proxy screen stays hidden.

## Non-goals

- **WireGuard or any other VPN on persovps.** Decided before this phase: it looks like a VPN,
  needs a key per customer, and fights the Premiumize VPN for Android's one VPN slot.
- **Changes to the Premiumize VPN.** It stays as 0.6 built it, either/or with the proxy.
- **Changes to the Squid logins or who may use the proxy.** Same `kb<clientNumber>` logins, same
  login file, same 15-minute refresh.
- **The provider's 407 answers on reconnect.** They come from the provider, not Squid (memory
  `antoine-homsi-france-block`), and have nothing to do with TLS.
- **Hiding the proxy's name in the first message (Encrypted Client Hello).** Neither Squid nor
  Android's TLS supports it in a usable way today.
- **Closing port 38129 inside this phase.** It stays open until every proxy customer's TV runs a
  version with the relay; Kevin closes it later.
- **A second proxy server.** Moving load off persovps is the Premiumize VPN's job.

## Decisions

- **Approach C: a second address, the proxy alone on its port 443**, over A (a separate port such
  as 8443 on the current address) and B (port 443 shared with the websites by name through
  nginx's stream module). C gives port 443 without rebuilding how the 11 websites get traffic,
  and blocking the proxy's address does not block kevbox.dev. A was the smallest change but uses
  an unusual port; B touches every live website, tv.kevbox.dev's app updates included.
- **A local relay in the app**, over teaching the players to speak to an encrypted proxy.
  OkHttp (ExoPlayer's network library) and mpv only speak plain HTTP proxies.
- **Squid handles the TLS itself (`https_port`)**, over stunnel or nginx in front of 38129.
  Squid then still sees each customer's real address, so its log and the fail2ban jail keep
  working with no extra plumbing. persovps's Squid 6.13 is built with GnuTLS, which supports a
  TLS port for forward proxying. (My call.)
- **New columns for the encrypted address**, over reusing `proxy_host` and `proxy_port`. Old app
  versions read those two and must keep getting the plain address until they update.
- **A Let's Encrypt certificate checked against Android's roots**, over a self-signed one pinned
  in the app. It looks like any website's certificate to an observer, certbot already runs on
  persovps, and the app's minimum Android (8.0) trusts Let's Encrypt's root. (My call.)
- **persovps's second address is `45.146.255.87`** (ZAP-Hosting, in `45.146.252.0/22`), from
  Kevin on 2026-11-10. As of that day it is not on the server: the host's boot data disk
  (`/dev/sr0`, `network-config`) still lists only `185.223.31.163`. A reboot from inside the
  server at 13:24 that day did not add it, and while it was pinged from outside, `tcpdump` on
  `eth0` saw no packet or address lookup for it, so ZAP's network did not yet send it to this
  server. Every service, container and port came back after that reboot. A restart from the ZAP
  panel that refreshes the boot data would make cloud-init treat the server as new: the hostname
  and `/etc/hosts` stay the same, SSH host keys are kept (`99-kevbox-keep-hostkeys.cfg`), and
  root's password and authorized keys are reset to the panel's.

## Open questions

- How does `45.146.255.87` get onto persovps: a file in `/etc/network/interfaces.d/` added by
  hand, or a restart from the ZAP panel after ZAP adds it to the boot data? Which netmask and
  gateway does ZAP give for it?
- Which name does the proxy use? It shows in the clear in each connection's first message: a
  `kevbox.dev` subdomain, or a separate plain-looking domain?
- How does the rollout move: every proxy customer at once as their TV updates, or a list of
  client numbers in kevbox.dev's settings (Kevin's TV first, then one customer at a time)?
- When the encrypted connection fails (persovps down, certificate problem), should the TV fail
  as a dead plain proxy does today, or briefly use the plain port? AC-16 assumes fail.
- What does a stranger who connects to `45.146.255.87:443` and pokes at it see: Squid's error
  page, or nothing?
- When does 38129 close: once every proxy customer's TV reports a relay version, at Kevin's word?
- Should Kevin's customer window say whether a TV uses the encrypted path (for Kevin only)?
