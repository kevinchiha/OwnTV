# 0.7-encrypted-proxy: design

## Goal

A KevBox Live customer with the VPS proxy switched on reaches persovps over an encrypted (TLS)
connection on port 443 of persovps's second address, so an internet company that inspects their
traffic sees ordinary HTTPS. It no longer sees the provider's address, the channel links (which
carry the customer's IPTV login) or the proxy password. The customer sees nothing new.

## Scope

- **persovps (server, every change gated):** the second public address `45.146.255.87` set up on
  `eth0` and kept across reboots. nginx's `listen 443` lines pinned to `185.223.31.163` so port
  443 on the new address is free. Squid gets a TLS port, `https_port 45.146.255.87:443`, with the
  same login file and rules as today's `http_port 38129`. A Let's Encrypt certificate for the
  proxy's name, renewed by certbot with a hook that reloads Squid. The `squid-auth` fail2ban jail
  covers port 443 too. These changes are written in the kevbox repo as config files and a runbook
  (`deploy/squid-tls/`); applying them waits for Kevin each time.
- **kevbox (kevbox.dev, branch base `main`):** migration `0024_live_proxy_tls.sql`, which adds the
  encrypted address to `member_playlist`, and the same two columns in the `member_playlist`
  table of `packages/core/test/schema.sql`. The proxy writes (`src/server/admin/live-proxy.ts`
  `writeVpsProxyToLive`, `src/server/admin/live.ts`, `src/lib/vps-proxy.ts` `vpsProxyEndpoint`)
  fill it from new environment settings, and `packages/core/src/liveVpn.ts` `turnLiveVpnOn`
  clears it with the other proxy columns.
- **Depends on 0.6.** 0.7 builds on 0.6's Realtime subscription, its automatic channel restart
  (0.6 AC-40), its VPN either/or (0.6 AC-25), migration 0023 and its column fallback. The build
  starts only once 0.6 is merged into `kevbox-live` and `main`; on live Supabase, 0023 lands
  before 0024.
- **OwnTV app (`kevbox/` layer, branch base `kevbox-live`):** a local relay in
  `kevbox/network/` that listens on 127.0.0.1 and wraps each connection in TLS to persovps.
  `ManagedProxy` points Core's proxy at the relay when the playlist carries an encrypted address.
  `SupabaseApi` and `KevBoxModels` read the new columns, with one more fallback step for a server
  without 0024. Wiring in `KevBoxCoordinator` and `di/KevBoxModule`.

## How it works

1. Kevin switches the VPS proxy on in the customer window, exactly as today. kevbox.dev writes
   the plain address (`proxy_host`, `proxy_port`) as before, for app versions without the relay,
   and the encrypted address (`proxy_tls_host`, `proxy_tls_port`) beside it.
2. The TV hears of it within seconds through 0.6's Realtime subscription. A version with the
   relay starts it on 127.0.0.1 and saves Core's proxy as `127.0.0.1:<relay port>` with the same
   `kb<clientNumber>` login. ExoPlayer, mpv, the guide and the logos all use Core's one proxy
   setting, so all of them go through the relay.
3. For each connection a player opens to the relay, the relay opens one TLS connection to
   `proxy_tls_host:443`, sends the proxy's name, checks the certificate, and copies bytes both
   ways unchanged. The player's proxy request, login included, travels inside the TLS.
4. Squid on `45.146.255.87:443` takes off the TLS and handles the request exactly like one on
   38129: same login file, same On / not cancelled / not expired rule, same blocked
   destinations.
5. Old app versions keep using `185.223.31.163:38129` in the clear until they update through the
   silent self-update. 38129 closes later, at Kevin's word.

What an internet company sees: a TLS connection to `45.146.255.87:443`, the proxy's name in its
first message, and the volume and timing of the traffic. No address of the provider, no link,
no login.

## Acceptance criteria

### persovps: second address and encrypted port

- **AC-1** `45.146.255.87` answers on persovps beside `185.223.31.163`, and still does after a
  reboot. Its config lives in a file that cloud-init (the tool that rewrites
  `/etc/network/interfaces.d/50-cloud-init` from the host's data) does not overwrite.
- **AC-2** Every nginx `listen 443` line names `185.223.31.163`; the IPv6 lines stay as they are.
  Before and after the change, each of the 11 sites in `/etc/nginx/sites-enabled` answers on
  `https://<its name>/` with the same status code, and the catch-all still closes unknown names.
  Port 80 is unchanged.
- **AC-3** Squid listens with TLS on `45.146.255.87:443` and keeps `http_port 38129`. Through the
  TLS port, a request with an On `kb<clientNumber>` login gets the destination's answer; a wrong
  password gets Squid's 407; a destination in the blocked list (now including `45.146.255.87`)
  gets 403. A plain-text connection to the TLS port gets no proxy answer.
- **AC-4** The TLS port accepts TLS 1.2 and 1.3 and refuses 1.0 and 1.1, with the Let's Encrypt
  certificate for the proxy's name, its chain ending at ISRG Root X1 (certbot
  `--preferred-chain "ISRG Root X1"`). `certbot renew --dry-run` passes, and a renewal reloads
  Squid through a deploy hook, so the new certificate is in use without a manual step.
- **AC-5** The `squid-auth` jail bans on port 443 as well as 38129: 10 wrong passwords in 10
  minutes over TLS ban the address for 1 hour, as today.
- **AC-6** Squid's access log records the customer's real address for TLS connections, as it does
  for 38129.
- **AC-28** Squid's answers carry neither its name nor its version: `httpd_suppress_version_string
  on`, and error pages with no Squid branding, on both ports.
- **AC-7** The build writes every server change as a file in `deploy/squid-tls/` plus a runbook
  that lists the steps in order, each with its check and its undo. The files start from
  persovps's current config, read over SSH without changing anything. The runbook warns that a
  site added later with `certbot --nginx` gets an unpinned `listen 443`, which stops nginx from
  starting while Squid holds `45.146.255.87:443`. Nothing is applied to persovps without Kevin's
  go-ahead at the time.

### kevbox.dev

- **AC-8** Migration `0024_live_proxy_tls.sql` adds `proxy_tls_host text` and
  `proxy_tls_port int` and `proxy_tls_addr text` (the proxy's IPv4 address) to
  `member_playlist`. Host and port both null means no encrypted address. Members read
  them on their own rows under the existing lock rule (0013), and nothing while locked.
- **AC-9** When kevbox.dev writes a proxy that is on for a customer whose client number is on
  the list `VPS_PROXY_TLS_CLIENTS` (comma-separated client numbers, or `all`; empty or missing
  means nobody), it also writes `proxy_tls_host`, `proxy_tls_port` and `proxy_tls_addr` from
  `VPS_PROXY_TLS_HOST`, `VPS_PROXY_TLS_PORT` and `VPS_PROXY_TLS_ADDR` in `/etc/kevbox-www/env`
  (`northcache.uk`, `443`, `45.146.255.87`). `VPS_PROXY_TLS_ADDR` is optional: missing or not a
  valid IPv4 address writes `proxy_tls_addr` as null. For a customer not on the list, or when the
  host or port setting is missing or invalid, it writes all three as null and the plain proxy
  works as today. Switching the proxy off clears all three, the same way it clears the plain
  fields.
- **AC-26** The 15-minute refresh (`scripts/refresh-vps-proxy-access.ts`) also brings every
  `member_playlist` row whose proxy is on into line with AC-9: it fills the encrypted address for
  customers on the list and clears it for customers off it. It writes only rows whose three values
  differ from what AC-9 gives, so an unchanged row is never rewritten and its TV gets no Realtime
  change. Removing a client number from the list, or emptying it, moves that TV back to the plain
  proxy within one refresh.
- **AC-10** Every place that writes the proxy fields of `member_playlist` today writes the
  encrypted address by the same rule as AC-9: the switch (`setKevboxLiveProxy` →
  `writeVpsProxyToLive`), Send to KevBox Live (`sendToKevboxLive`), and the delete and
  client-number-change paths in `src/app/actions.ts`. Turning the VPN on (`turnLiveVpnOn`) clears
  the encrypted address with the plain one. 0.6's either/or with the VPN is unchanged.
- **AC-11** The customer window shows the same VPS proxy switch with no new control.
- **AC-29** In the customer window's KevBox Live box, a TV's status line shows "encrypted" when
  that customer's row carries an encrypted address and the TV's last reported app version is at
  or above the first version with the relay (a constant in kevbox.dev, set when 0.7 is
  released). It shows nothing new otherwise. The TV reports nothing new for this.

### OwnTV app

- **AC-12** The playlist read asks for `proxy_tls_host`, `proxy_tls_port` and `proxy_tls_addr` with the proxy
  columns. A server without 0024 refuses them; the app then asks without them and reads the
  proxy as plain, the same fallback pattern as 0.6's AC-23.
- **AC-13** When the visible playlist's proxy is on and carries a valid encrypted address
  (non-blank host, port 1-65535), the app runs the relay and saves Core's proxy as
  `127.0.0.1:<relay port>` with the playlist's proxy login. The plain `proxy_host` is never saved
  into Core's setting in this case.
- **AC-14** The relay listens on 127.0.0.1 only, so other devices on the home network cannot use
  it.
- **AC-15** For each accepted connection, the relay opens a TLS connection to
  `proxy_tls_addr:proxy_tls_port` with no DNS lookup, or, when `proxy_tls_addr` is null, to
  `proxy_tls_host:proxy_tls_port` through DNS. Either way it sends `proxy_tls_host` as the server
  name, and checks the certificate
  and the host name against the same roots Core trusts: Android's own plus Core's bundled
  Let's Encrypt roots (`ExtraTrustAnchors`, `isrg_extra_roots.pem`). It then copies bytes both
  ways unchanged, and closing either side closes the other.
- **AC-16** A certificate that fails the check, or a TLS connection that fails, closes the
  player's connection. The relay never falls back to the plain port or to a direct connection.
- **AC-17** The relay's port stays the same for the life of the app process, so coming back to
  the app or a playlist re-check does not rewrite Core's setting and restart the channel. The
  relay tries one fixed port first and takes a free one only when that is busy.
- **AC-25** The TV keeps the last encrypted address it applied, beside Core's saved proxy. When
  the app process starts (opening the app, or the home-rows job at boot), the relay starts from
  that address before any playlist fetch, so Core's saved `127.0.0.1` setting never points at a
  dead port while kevbox.dev is unreachable. If the relay has to take a different port, it
  updates Core's setting at once.
- **AC-18** A proxy with no encrypted address (server without 0024, settings missing) is applied
  as a plain proxy, exactly as today.
- **AC-19** When the encrypted address appears, disappears or changes through Realtime while a
  channel plays, Core's proxy and the relay's target are updated and the channel restarts by
  itself, by 0.6's AC-40 rule. A change to the encrypted host or port alone counts as a change,
  even though Core's saved `127.0.0.1:<port>` stays the same.
- **AC-20** The relay stops when the proxy is switched off, when the VPN takes over (0.6 AC-25),
  and on sign-out.
- **AC-21** KevBox's own server calls (`SupabaseApi`, `NO_PROXY`) never go through the relay.
- **AC-27** The silent self-update (`kevbox/release/`: the version check and the APK download)
  goes straight to the internet, with no proxy and no relay, the same way `SupabaseApi` does. A
  relay that fails closed (AC-16) can then never block the update that fixes it.
- **AC-22** ExoPlayer and mpv both play a channel through the relay, checked on the `kevbox_tv`
  emulator against a local TLS proxy.
- **AC-23** The "proxy in use" flag in error reports and play notes (`ProxyInUse`) reads true when
  the relay carries the traffic, as it does for the plain proxy.
- **AC-24** Nothing new appears on the TV screen. The app's own Proxy screen stays hidden.

## Non-goals

- **WireGuard or any other VPN on persovps.** Decided before this phase: it looks like a VPN,
  needs a key per customer, and fights the Premiumize VPN for Android's one VPN slot.
- **Changes to the Premiumize VPN.** It stays as 0.6 built it, either/or with the proxy.
- **Changes to the Squid logins or who may use the proxy.** Same `kb<clientNumber>` logins, same
  login file, same 15-minute refresh.
- **The provider's 407 answers on reconnect.** They come from the provider, not Squid (memory
  `antoine-homsi-france-block`), and have nothing to do with TLS.
- **Hiding the proxy's name in the first message (Encrypted Client Hello).** Neither Squid nor
  Android's TLS supports it in a usable way today.
- **Closing port 38129 inside this phase.** It stays open until every proxy customer's TV runs a
  version with the relay; Kevin closes it later.
- **A second proxy server.** Moving load off persovps is the Premiumize VPN's job.
- **Cloudflare in front of the proxy or the websites.** Its terms forbid serving video through
  its CDN without its paid video products, a raw proxy needs its paid TCP product (Spectrum),
  every stream would pass through a company that acts on anti-piracy complaints, and in Spain
  LaLiga's court order has the big internet companies block Cloudflare addresses during matches
  (still in force at the start of the 2026-27 season). Cloudflare for the websites alone is a
  separate idea for later: persovps's address is already public in old DNS records, and nobody
  has attacked kevbox.dev so far.
- **Hiding from someone who probes the port.** A stranger who connects to `45.146.255.87:443`
  without a login gets Squid's "proxy login required" answer, so they can tell a proxy is there.
  Hiding that needs a different front program, which breaks "the same Squid", and the internet
  companies in question block by address and name rather than probing (grill round 1). AC-28
  removes Squid's name and version only.

## Decisions

- Size: 29 criteria, within the cap
- **Approach C: a second address, the proxy alone on its port 443**, over A (a separate port such
  as 8443 on the current address) and B (port 443 shared with the websites by name through
  nginx's stream module). C gives port 443 without rebuilding how the 11 websites get traffic,
  and blocking the proxy's address does not block kevbox.dev. A was the smallest change but uses
  an unusual port; B touches every live website, tv.kevbox.dev's app updates included.
- **A local relay in the app**, over teaching the players to speak to an encrypted proxy.
  OkHttp (ExoPlayer's network library) and mpv only speak plain HTTP proxies.
- **Squid handles the TLS itself (`https_port`)**, over stunnel or nginx in front of 38129.
  Squid then still sees each customer's real address, so its log and the fail2ban jail keep
  working with no extra plumbing. (My call.) Tested 2026-11-10 in a throwaway `debian:trixie`
  container with the same Squid 6.13 (GnuTLS build) as persovps: through `https_port`, a good
  login got 200, a wrong password 407, an HTTPS site through CONNECT 200, and plain text got no
  answer. With no TLS option set it accepts TLS 1.2 and 1.3 and refuses 1.0 and 1.1.
  `tls-min-version=1.2` makes this build exit at start (`FATAL: ... in TLS options`), and
  `tls-options=NORMAL:-VERS-TLS1.0:-VERS-TLS1.1` makes the port refuse every client, so the config
  sets neither.
- **The relay starts at app start from the last applied address** (AC-25), over starting it only
  after a playlist fetch. Otherwise a TV that starts while kevbox.dev is unreachable would point
  every request at a dead `127.0.0.1` port, and the start-up provider check (`ExpiryMonitor`)
  would send false error reports. The TV already keeps the proxy password in Core's settings.
  (My call.)
- **The build reads persovps's config over SSH, read-only**, to start the `deploy/squid-tls/`
  files from what is there (AC-7), over Kevin pasting it in. (My call.)
- **New columns for the encrypted address**, over reusing `proxy_host` and `proxy_port`. Old app
  versions read those two and must keep getting the plain address until they update.
- **A Let's Encrypt certificate checked against Android's roots**, over a self-signed one pinned
  in the app. It looks like any website's certificate to an observer, certbot already runs on
  persovps, and the app's minimum Android (8.0) trusts Let's Encrypt's root. (My call.)
- **persovps's second address is `45.146.255.87`** (ZAP-Hosting, in `45.146.252.0/22`), from
  Kevin on 2026-11-10. As of that day it is not on the server: the host's boot data disk
  (`/dev/sr0`, `network-config`) still lists only `185.223.31.163`. A reboot from inside the
  server at 13:24 that day did not add it, and while it was pinged from outside, `tcpdump` on
  `eth0` saw no packet or address lookup for it, so ZAP's network did not yet send it to this
  server. Every service, container and port came back after that reboot. A restart from the ZAP
  panel that refreshes the boot data would make cloud-init treat the server as new: the hostname
  and `/etc/hosts` stay the same, SSH host keys are kept (`99-kevbox-keep-hostkeys.cfg`), and
  root's password and authorized keys are reset to the panel's.
- **How ZAP puts the second address on persovps** (found 2026-11-10 after Kevin restarted it from
  the ZAP panel at about 13:31): ZAP's panel runs `ip addr add 185.223.31.163/32 dev eth0` and
  `ip addr add 45.146.255.87/32 dev eth0` through the QEMU guest agent at start. The boot data
  disk and cloud-init are unchanged (same instance-id, same `network-config`), so nothing on the
  server holds the address. The reboot from inside the server at 13:24 got no such commands, so
  only a panel start adds it. After the panel restart `45.146.255.87` answered pings, outgoing
  traffic from it left as `45.146.255.87`, and every service, container and port came back. No
  gateway of its own is needed: replies leave through `185.223.31.1`.
- **AC-1's boot step is already on persovps** (Kevin's go-ahead, 2026-11-10 13:40). A second
  reboot from inside at 13:37 confirmed the address was lost without it. The step is the systemd
  unit `/etc/systemd/system/kevbox-second-ip.service`: a oneshot running
  `ip addr replace 45.146.255.87/32 dev eth0`, ordered after `networking.service` and before
  `network-online.target`, `squid.service` and `nginx.service`, enabled for `multi-user.target`.
  A unit was picked over a second `iface eth0` stanza in `/etc/network/interfaces.d/` because
  `replace` succeeds whether or not ZAP's panel already added the address, and the ordering puts
  the address in place before Squid binds to it. Its undo is in the file's header. The build
  copies it into `deploy/squid-tls/` and the runbook marks the step done; AC-1's reboot check
  still runs once the rest is applied.

- **Customers move over through the 15-minute refresh and a client-number list** (grill round 1,
  AC-9, AC-26), over a one-off fill script (all at once, and undoing it is another script) and
  over Kevin flipping each customer (manual, error-prone). The list `VPS_PROXY_TLS_CLIENTS`
  starts with Kevin's client number only. One list is the rollout plan, the fill for customers
  already on, and the off switch: emptying it puts every TV back on the plain proxy within 15
  minutes. The refresh starts writing `member_playlist`, which it did not before.
- **The encrypted path fails closed, and the self-update skips the proxy** (grill round 1,
  AC-16, AC-27), over falling back to the plain port. A fallback would hand an inspecting
  internet company exactly what 0.7 hides, and 38129 could never close. Internet companies block
  the IPTV provider, not GitHub, so a direct self-update reaches these TVs. Kevin hears of
  failures through the existing "can't watch" Telegram ping.
- **Squid's name and version are hidden; probing is accepted** (grill round 1, AC-28,
  Non-goals).
- **0.6 is released on its own first; 0.7 is a later release** (grill round 1), over one release
  for both: a fault then points at one phase, and the VPN customers do not wait for 0.7.
- **Kevin's customer window marks encrypted TVs** (grill round 1, AC-29), worked out from the
  row and the TV's reported app version, with no new reporting from the TV. The same data later
  shows when every proxy customer has updated.

- **The proxy uses a separate, plain-looking domain bought for it alone** (grill round 2), over
  a `kevbox.dev` subdomain. The name travels in the clear; a kevbox.dev name leads in two clicks
  to tv.kevbox.dev, which hands out `KevBoxLive.apk`, and public certificate logs would list it
  beside `tv.`, `streams.`, `stremio.` and `admin.kevbox.dev`. A name-based block on one domain
  then never takes down the other, and a burned name is replaced through `VPS_PROXY_TLS_HOST`
  with no app release. Auto-renew and the registrar's owner privacy are on. Kevin buys it at
  Namecheap; its DNS has one A record pointing at `45.146.255.87`.
- **38129 closes at Kevin's word once every customer whose proxy is on has shown "encrypted"
  (AC-29) for 7 days in a row** (grill round 2). The runbook says so; closing it (Squid's
  `http_port 38129` and its ufw rule) is not part of 0.7's build.
- **Cloudflare stays out of 0.7** (grill round 2, Non-goals).

- **The proxy's domain is `northcache.uk`**, bought by Kevin at Namecheap on 2026-11-10 (grill
  round 3), over the $1-first-year extensions (`.xyz`, `.site`, `.online`, `.ink`). Those renew
  at about $19-39 a year and carry spam reputations that get whole extensions blocked by some
  filters; `.uk` renews at about $10 with a clean reputation. The bare name is the proxy's name:
  one A record to `45.146.255.87`, and a CAA record allowing only Let's Encrypt.
- **The TV connects to the proxy by address, with no DNS lookup** (grill round 3, AC-15), over
  looking the name up. DNS blocking (the usual tool of French IPTV court orders, and of router
  and "safe browsing" filters) then cannot touch the proxy; the name is used only for the server
  name and the certificate check. A changed address reaches TVs through `VPS_PROXY_TLS_ADDR` and
  the 15-minute refresh.

## Open questions
