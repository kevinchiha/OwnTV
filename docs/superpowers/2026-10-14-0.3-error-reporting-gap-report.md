   - Both JSON files are copied verbatim from the plan's Shared contract section (Task 1 for OwnTV, Task 9 for kevbox).
   - LiveErrorCodesTest (Task 1) and live-error-labels.test.ts (Task 9) pin each repo's label list to that same contract. That is the "test checks that the two lists match" which AC-33 asks for, so AC-33 does not depend on the release pre-flight.
   - In "After the build", kevbox.dev is deployed (step 3) before `release.sh` runs (step 4). The live site that has to label the codes is already running the Task 9 map when the app ships.
   - The claim that the file is normally missing at release time does not fit that order either. By then kevbox has been merged and deployed, so a checkout without the file is just an out-of-date local copy, which the warning reports.

At most this is a wording tidy-up. No user-visible failure can get through unnoticed.

### db-5 (minor)

**Claim.** Task 8's AC-28 test intent as written dereferences null: getMemberActivity returns null for a member with only live_error rows (no daily rows, no heartbeat), so '.errors7d stays 0' throws. Written with '?.errors7d ?? 0' instead, it passes vacuously and proves nothing. The test needs a member_heartbeat or member_activity_daily row seeded so the function returns an object.

**Refuter.** The facts in the finding are correct. getMemberActivity returns null when a member has no member_activity_daily rows and no heartbeat (activity.ts:38). Plan line 793 says to seed only live_error rows and check that errors7d stays 0. So a test written exactly that way would hit null.

It still doesn't count as a plan gap.
1) This is a detail of a test body, and the plan deliberately leaves test bodies out. The test intent names the behaviour to prove (live_error never feeds errors7d). How to set up the member is the implementer's call.
2) Written the obvious way (`.errors7d`), the test throws on its first run, so someone notices at once and seeds a heartbeat or daily row. Nothing goes wrong silently.
3) The "passes vacuously" worry only applies to the member half. The same intent also checks getFleetStats(...).errors7d, which never returns null (activity.ts:95-111). That half genuinely proves live_error rows don't leak into the fleet count.
4) The behaviour being guarded is close to impossible to break by accident. Both errors7d queries read only `public.member_event where kind='playback_error'` (activity.ts:35, :101). Plan line 789 also says every activity.ts query stays unchanged. If an edit made live_error leak in, the fleet half of the test would catch it.

A loose spot in a test-setup detail that fails loudly is not a gap a user would ever feel.

### db-6 (minor)

**Claim.** record_live_errors with a null p_device_id raises a not-null violation, and the TV drops that batch after 3 tries. The behaviour list guards a blank device id only for record_live_checkin, while its own rule says 'No cast may raise on bad input'.

**Refuter.** The finding quotes the plan correctly. live_error.device_id is `text not null` (plan:623). Rule 4 only caps device_id at 64 characters (plan:704). The blank-device-id guard covers only record_live_checkin_as (plan:708). AC-17 drops a batch after 3 tries on a 4xx other than 401 (spec:113-116; plan:380).

The harm it describes can't happen, though, because the TV can never send a null device id. Task 2 types the id as a non-null Kotlin `String`: `recordLiveErrors(accessToken, deviceId: String, ...)` and `DeviceId.get(): String`. That value is a random UUID made on the first call and kept the same after that (plan:256-261, 282). Task 3's ErrorSender takes the same DeviceId single (plan:353). The contract body is `"p_device_id": "<uuid>"` (plan:60). So no batch from the TV ever hits the not-null rule, and none gets dropped for that reason.

An empty string would not trigger the error either: `left('', 64)` is `''`, which is not null. Only someone calling the API by hand with a null could raise it, and they would just get the error back. No stored data is lost and no member is affected.

The finding also misreads 'No cast may raise on bad input'. That rule is about type casts on the entry fields (dates, integers). It says nothing about a not-null check on a column. The gap does exist, but only as a matter of tidiness. It does nothing a user would notice. If I didn't refute it outright, it would rank no higher than minor.

### web-3 (minor)

**Claim.** AC-34 asks for route tests for 'both views' (the customer window and the Live errors page) plus the empty case. Task 10 reads 'both views' as summary and rows. The member route that feeds the customer window gets only the 401 and empty-list intents, with no intent that it calls listMemberLiveErrors and listMemberLiveDevices for the resolved member's userId. requireMember resolves by id or email (members.ts:28), so passing the raw path segment instead of member.userId would go unnoticed.

**Refuter.** The facts the finding cites are accurate, but the harm it describes cannot reach a user. Plan line 931 does read "both views" as summary and rows. Behaviour 3 (line 922) has the member route call requireMember and then both list functions, and no test intent checks which id those functions receive. requireMember passes the decoded path segment to getMember, and getMember matches on id or email, so the finding is right about that.

The finding is a missing test, though, and the slip it worries about would not change anything a user sees. The only caller of this route is Task 11's customer window. It passes status.loginId (plan lines 961 and 968), and that value comes from findLoginId, which returns kevbox_auth_users.id, the user's uuid (a unique id string). For that caller the raw path segment, once decoded, is exactly member.userId. A route that passed the raw segment would query the same rows. Email lookups only reach this route if someone types the URL by hand. On top of that, every sibling member route (activity, watch, devices and the rest) already follows the pattern of passing member.userId after requireMember, and Task 10's behaviour 1 tells the builder to copy that existing route shape. The finding names a test gap. It does not name a bug a user would hit, so under the rules it is refuted.

### web-4 (minor)

**Claim.** AC-39 says each usage list entry links to the customer window. Task 8's seen7d, quiet and versions lists can hold a login with no member_playlist row (empty clientNumbers), and Task 12's behaviour states the no-link fallback only for error rows, not for usage list rows. Such a member shows an email with no way to reach a customer window, and no task says what the row should do.

**Refuter.** The facts the finding cites are accurate. Plan Task 8 behaviour 5 builds seen7d and quiet from live_device alone. Task 12 states the "email only, does not navigate" fallback only for error rows. AC-39 says each list entry links to the customer window. What does not hold is the claim that "no task says what the row should do."

Task 12 behaviour 5 defines a usage list row as: email, then "Client {n}" links, then "Last seen {date}". The links come from the member's clientNumbers, one per number, the same wording the error rows use. If clientNumbers is empty, the row shows the email, no links and the last-seen date. That outcome is fully determined.

The error-row fallback had to be spelled out because error rows also navigate when you click the row itself, which needs a first client number. Usage list rows have no row-click behaviour at all, so an empty list leaves nothing undefined.

AC-39 says "as in AC-32", and the spec's own resolved decision (spec lines 344-346) links rows by `member_playlist` client number. So a login with no playlist row has no client number to link to under the spec as well. The plan copies the spec's chosen rule; it does not leave a hole in it.

What remains is a wish for a different link target, such as linking by email, for an edge case the spec already accepts. The plan does not leave that case unspecified. Since I was told to refute when unsure, I refute.

### web-5 (minor)

**Claim.** Task 12's test intents say 'fetch mocked', but the existing admin views (FleetView) reach the API through the `api` client in src/lib/admin/api.ts, and their tests mock that module. The plan names no `api` methods for /api/live-errors, /rows or /usage, nor for the member route Task 11 uses. Two web tasks can each pick a different fetch path, and the tests then mock different layers.

**Refuter.** The facts in the finding are correct, but the gap it describes cannot cause a problem. FleetView does call the API through the shared `api` client, and its test mocks `@/lib/admin/api`. Tasks 11 and 12 name only routes, not `api` methods, and Task 12's intent does say "fetch mocked".

What it would actually cost is small. Tasks 11 and 12 build two separate components, each with its own test file, and neither test touches the other's component. If one task mocks `api` and the other mocks plain `fetch`, both tests still prove their own component, and nothing breaks for a user. The worst case is two styles in one codebase.

Task 12 also tells the builder to "Follow the Fleet page's structure", and that points to `fleet-view.tsx`, which imports `api`. So the plan already steers the builder toward the client. Task 11's component sits in `src/components/` next to `kevbox-live-section.tsx`, which goes through server actions in `live-actions.ts`, not the admin `api` client. That makes the choice of fetch path there an ordinary implementation detail. Naming the `api` methods would be implementation-body detail that the plan leaves out on purpose. This is a style note, not a gap.
