- Task 7 · `scripts/prove-live-vpn.sh` (AC-5): grants `kevbox_admin` and `authenticated` to `postgres` on the throwaway stack and never revokes them; a second run on the same stack inherits them.
- Task 8 · `packages/core/src/liveVpn.ts` (AC-8): `inTransaction` given a checked-out client only takes the advisory lock and opens no transaction; callers must pass the pool or a client already in a transaction.
- Task 8 · `src/server/admin/__tests__/live.test.ts` (AC-12): test name claims "clears all four fields" but checks only the call order (the core test checks the clearing).
- Task 8 · `packages/core/src/liveVpn.ts` (AC-8): `setVpnServerBackup` with an unknown backup host throws a raw foreign-key error; the admin action should catch it or check first.
- Task 9 · `src/app/vpn-actions.ts` (AC-6): runFetch drops a second file whose remote line names a host already seen, to avoid upserting one row twice, but it does not add that file's premiumizeVpnHost(code) to `failed`. If Premiumize ever pointed two files at one host, that server would vanish from the result with no 'Couldn't fetch' line. Today's 18 files all have different hosts, so nobody hits this now. A one-line push to `failed` would make it visible.
- Task 9 · `src/components/vpn-servers-view.tsx` (AC-6): When a refetch fails as a whole (success false, or the call throws), the view shows a toast but leaves the previous run's 'Couldn't fetch <host>' lines on screen. Those lines then describe the old fetch, not the latest attempt. This is cosmetic; the toast does report the real error.
- Task 10 · `src/app/live-actions.ts` (AC-11): Turning the VPN on reads the Debrid sheet through fetchDebridMetadata, which keeps a 5-minute cache. The constraint says the login is read at click time so that a login changed a minute ago is the one written. Changes made through the admin site's debrid actions clear that cache, so in normal use this holds. A change made straight in the workbook, though, could take up to 5 minutes to show, and the old Customer ID and API key would be written in that window. Calling invalidateCache (or a no-cache read of the Debrid sheet) before the turn-on read would close the gap, if that case matters.
- Task 10 · `src/components/kevbox-live-section.tsx` (AC-10): The switch is disabled only while it is both blocked and off (`vpnLocked = vpn.blocked !== null && !vpn.on`). Read literally, AC-10 disables it whenever there is a reason. The deviation is on purpose (a code comment says so, and a test covers it) so that a VPN that is already on can always be turned off. That looks like the right behaviour, but it should be recorded as a deliberate deviation.
- Task 10 · `src/app/live-actions.ts`: The turn-on path of setKevboxLiveVpn repeats the customer and row lookup from loginWithRow inline, because it also needs the full Sheet1 rows for groupDebridAccounts. The section also keeps its own VPN_AUTO = "auto" instead of using core's, which the browser cannot import. Both are small duplications that could drift apart; neither is a bug today.
- Task 10 · `src/lib/vpn-status.ts` (AC-15): The 'next try' time is formatted with beirutTime(next, next), so it never shows a date, even when the retry falls on another day than the one being viewed (for example an old fell_back event). This matches the spec's example ('next try 00:05') and a code comment explains it. Showing only the time of day can mislead for an event several days old, but the status line shows the stored state as AC-15 asks.
- Task 11 · `src/server/admin/vpn-login-sync.ts` (AC-21): The quiet-hours check (QUIET_UNTIL_HOUR = 8, plus a new Beirut-hour Intl formatter) copies the private quietHours in src/lib/watch-messages.ts instead of sharing it. If the 00:00-07:59 rule ever changes, the two copies can drift apart, and AC-21 says every VPN message follows the same rule. Exporting one helper from watch-messages.ts would fix it, but that file is not on this task's Files list, so it waits for the owner after the merge.
- Task 11 · `src/server/admin/vpn-login-sync.ts`: syncVpnLogins builds its own client-number-to-customer map next to the sheetByClientNumber(customers) result it already computes for watchCustomer. That is two lookups over the same Sheet1 data. It works, but it is extra code.
- Task 11 · `src/server/admin/vpn-login-sync.ts`: Rows are handled one after another with no catch per row. A database error on one row (from updateLiveVpnLogin or the turn-off transaction) stops the run, and later rows are skipped until the next action or the 15-minute run. That matches 'throw on failure' and the job pages on exit 1, but nothing records which rows were left unsynced. Noted, not a defect against the brief.
- Task 12 · `src/lib/vpn-messages.ts` (AC-18): The code adds a fall-back text the plan does not list: three or more hosts give '<a>, <b> and <c> all failed.' The plan gives forms for two hosts, one host and no host only. An 'auto' fall-back that tried more than two hosts would send this text. The behaviour is sensible, but nobody approved this wording and no test covers it. Owner to confirm the wording or fold it into the plan.
- Task 12 · `src/lib/vpn-messages.ts` (AC-20): The back-on message does not wait for the fall-back message it follows. Suppose a 'fell_back' and the 'connected' after it are both unsent in one run, and the fall-back send fails. The silent 'connected again' message still goes out and is marked sent. The next run then sends 'fell back ... Next try' after Telegram already said the TV is back on. This is a rare ordering glitch, not a spec breach.
- Task 12 · `src/lib/vpn-messages.ts`: customerFor() builds a stand-in customer (label = user id, link = /members?member=<userId>) for a user missing from the map. The route always builds every event's user with getWatchMember, so in production this code never runs. It also copies the member-link format from watchCustomer by hand, so the two could drift apart. Small dead-weight code.
- Task 12 · `src/lib/__tests__/vpn-messages.test.ts` (AC-18): The plan's test intent expects 'Next try 00:05' for a 21:05 fall-back. The test asserts 'Next try 11/11 00:05', because <next> = beirutTime(received_at + 3 h, now) and 00:05 falls on the next Beirut day. The code follows the plan's formula, so it is correct; the shorter wording in the test intent is just loose. The test also covers the after-midnight case, where the result is '00:05'. Recorded only so the owner knows the difference is deliberate.
- Task 12 · `src/lib/__tests__/vpn-messages.test.ts`: Two tests sort id arrays with a bare .sort(). That compares numbers as text, so 10 comes before 9. It works today only because ids are small and sorted the same way on both sides. Use .sort((a, b) => a - b) to make it robust.
