### tv-2 [important]

**Claim.** Task 2 Behaviour 4 clears the failure flag on any 2xx, including a retried pending note whose play happened before the failure. The next real play is then held back up to 60 minutes. The server keeps the incident open because the sent play is older than the failure, so Kevin gets a false 'can't watch' Telegram message while the customer is watching. The flag should clear only for failures recorded before the sent note was built, and no test intent covers this.

**Evidence.** Plan Task 2 Behaviour 4: 'A 2xx answer clears the pending note, sets lastSentAtMs = now() and clears the failure flag.' Behaviour 6: the pending note goes again on the 15-minute tick. Task 5 Behaviour 5(a) clears only when 'last_play_at > failure_last_at'. Example: play note pending from 10:00 (send failed), failure recorded 10:05, tick resends the 10:00 note at 10:10 → flag cleared, lastSentAtMs 10:10; a good play at 10:20 is not due; the incident opens at about 10:20 and stays until about 11:10.

**Touches.** task-2, fn:PlayNotes.onFailureRecorded, fn:playNoteDue, AC-4, AC-17, task-5

**Refuter.** Every quote in the finding matches the plan and spec, and the example timeline holds up when you walk through it.

In Task 2, Behaviour 4 clears the failure flag on any 2xx answer. It does not check when the note being sent was built. Behaviour 6 resends the old pending note on the 15-minute tick or when the app comes to the foreground. So a note built before a failure can clear a flag that the failure set after it.

The timeline:
- 10:00: a note is built. Its send fails, so it stays pending.
- 10:05: ErrorReporter records a failure, which sets the flag.
- 10:10: the tick resends the 10:00 note and gets a 2xx. The flag clears and lastSentAtMs becomes 10:10.
- 10:20: a good 30-second play. The flag is clear and only 10 minutes have passed, so the note is not due and nothing is sent. Behaviour 3 says "When not due, it does nothing".

On the server, the incident clears only when last_play_at > failure_last_at (spec lines 109-110; Task 5 step 5a). Here last_play_at is 10:00 on the TV clock, from p_played_at, and failure_last_at is 10:05, so nothing clears. The failure's received_at was about 10:05, so it qualifies and the incident opens around the 10:20 run (spec lines 105-107). Kevin gets a 🔴 "can't watch" message while the customer is watching. The next due note goes out at 11:10, and only then does a 🟢 "watching again" follow.

This breaks spec AC-4: after a failure, the next 30-second play must send its note at once. The defect is in Behaviour 4 as written, so this is more than a missing test. None of the Task 2 test intents covers a stale pending note sent after a failure. The intents check playNoteDue on its own (the pure function), the retry and replace sequence, and signed-out handling. So the bug could ship unnoticed, and Kevin would see it as a false alert. The fix is narrow: clear the flag only for failures recorded before the sent note was built, for example by keeping a failure time or counter and comparing it. Severity important is right. The false alert reaches a person and lasts up to about 50 minutes. It is not data loss, and a later play corrects it.

### check-1 [important]

**Claim.** A TV that keeps sending the same failure (same device, code and channel) at gaps under 5 minutes never opens an incident while the failures go on. Every server merge moves the row's received_at to now, so the qualifying row never gets 15 minutes old. The 'within 15 minutes' goal and AC-14 fail with no upper bound, not just 'run long'. **Touches.** decision:wait-from-received-at, fn:record_live_errors_as, task-4, task-5, AC-14, AC-15

**Refuter.** I checked every claim against the files and could not refute any of them.

1. The server merge keeps moving received_at. In 0015_live_error.sql:216-231, a new entry merges into the newest row with the same device, code and channel whose span overlaps or comes within 5 minutes of it (TV clock, lines 221-222). The update sets received_at = v_now (line 230). Nothing stores when the row was first received.

2. The open rule waits on that same received_at. Spec lines 105-107 and plan Task 5 step (b) (line 426) open an incident only when the qualifying row's received_at is at least 15 minutes old. With one row and no blocking failure, the qualifying row is the one whose repeat_count sum reaches 2, which is that same row.

3. The TV really does send that often while failures continue. ErrorSender.kt sends a batch 60 s after the oldest unsent entry (FIRST_WAIT_MS = 60_000, nextSendAtMs). So if a TV keeps failing on the same channel and code less than 5 minutes apart, a batch reaches the server every minute or two. Each batch merges into the row and resets received_at to now. The row never gets 15 minutes old, so no incident opens until the failures stop. The case the feature exists for (a customer who keeps trying and can't watch) is the one it misses, with no upper bound on the delay.

4. The spec says the wait "can only run long, never short" (lines 352-354). That is true but hides this case: the delay is not just long, it is unbounded. No task states the limit.

5. Plan Task 4 item 4 (line 327) re-creates record_live_errors_as "unchanged except" a proxy fix and adds no first-received time. Plan line 441 tests only one static row. Line 442 tests two separate rows or one row with repeat 2, never a row that keeps merging. The live check at line 742(b) moves received_at back with psql, which skips exactly this case.

This is a real behaviour gap, not just a missing test. It fails silently (no alert, nobody notices), and it hits the main goal: "within 15 minutes" (spec line 5) and AC-14/15. Important is the right severity.

### db-6 [important]

**Claim.** Task 5 puts the whole run in one transaction and says an insert that hits live_watch_incident_one_open 'counts as nothing opened, not as an error'. In Postgres, a unique violation inside a transaction aborts the whole transaction unless the insert uses ON CONFLICT DO NOTHING (or a savepoint). Catching the error in JS would leave the run's clears and advice updates rolled back. The plan never names the mechanism.

**Refuter.** The finding quotes the plan correctly. Line 426 says "in one transaction", line 434 says an insert that hits the index "counts as nothing opened, not as an error", lines 293-294 define the partial unique index, and the plan never writes ON CONFLICT or savepoint. The Postgres fact is also right: a caught unique violation leaves the transaction aborted.

It is still not a real gap. The plan states the required outcome (a race insert opens nothing and raises no error) and leaves out implementation bodies on purpose. Picking the SQL that delivers that outcome is implementation work. The kevbox core package already has an obvious way to do it: `on conflict ... do nothing` appears more than ten times in packages/core/src, in kevboxMember.ts, bulk.ts, migrate261.ts, reset.ts, addons.ts and access.ts. In that codebase, "an insert that hits a unique index counts as nothing, not an error" means ON CONFLICT DO NOTHING, which also works with a partial unique index (with no conflict target, or with `(user_id, device_id) where cleared_at is null`).

The failure the finding describes would not go unnoticed either. If someone caught the error in JS instead, the next query in the transaction (step c or d) would fail loudly with "current transaction is aborted" (Postgres code 25P02). That is a thrown error, not clears and advice updates quietly rolled back. It also needs two runs to overlap, which is rare. At most this is a one-word clarification worth adding (minor), not an important gap.

### check-3 [important]

**Claim.** Task 7 sends every database error to 500, and that includes markAlerted/markClearAlerted failing after Telegram answered 'sent'. The run then stops before the remaining messages, and the message already sent goes out again on every 5-minute run until marking works. first-login-check, the route Task 7 copies, treats the mark after a send as best effort for this reason.

**Refuter.** The quotes are accurate. Plan step 3 marks after each "sent". Step 4 sends any database error to 500. first-login-check does wrap its mark in a try/catch with the comment "Best-effort: a mark failure (rare) at worst re-announces once; never fatal". But the harm the finding describes is mostly overstated, and the plan's choice holds up.

1. "Goes out again on every 5-minute run until marking works" is mostly wrong. Every run starts with runWatchCheck, which reads and writes the same database. If the database is down, the next run fails at that step and sends nothing. The message goes out again only once the database works, and by then the mark works too. The usual cost is one repeat message. first-login-check accepts exactly that cost ("at worst re-announces once"). The case where it repeats every run is narrower: the database works but only the mark query keeps failing, such as a broken UPDATE. That is a code bug. Task 5's mark tests and the route tests should catch it, and every one of those runs returns 500, which pages through OnFailure. So nobody misses it.

2. The plan never says Task 7 copies first-login-check's mark handling. It cites first-login-check only for the secret gate (step 1) and for "the same shape" of the 500 response (step 4).

3. Stopping on a mark failure is arguably safer than carrying on. When a mark fails, the database is probably failing, so the later marks would fail too. Carrying on would send every remaining message without marking any of them, and they would all go out again on the next run. Stopping limits the repeats to one message. The unsent messages go out on the next run five minutes later, and Kevin gets paged.

4. The messages go to TELEGRAM_CHAT_ID, which env.example in the plan describes as "Kevin's chat id with the bot". A repeat lands on Kevin, who is also being paged, not on a customer.

At most the plan could say in one line what happens when a mark fails after a send. That is a small wording gap, not an important one.

### screens-2 [important]

**Claim.** Adding a Sheet1 read to GET /api/members/[userId]/live-errors with no stated fallback breaks the shipped box whenever the workbook read fails. Today the route never reads Sheet1. After Task 8, any fetchSheet1Data error while a TV has an open incident goes through shapeError as a 500, and KevboxLiveErrors then shows only 'Could not load KevBox Live errors', hiding the TV table and errors list. That happens exactly when a customer can't watch. The plan should say that a Sheet1 failure yields silenced=false (or omits rule 2) and still returns errors and devices, with a test for it.

**Refuter.** The finding reads the code correctly. Today the member route never reads Sheet1. Task 8 Behaviour 1 (plan:645) adds a Sheet1 read only when a TV has an open incident and says nothing about what happens if that read fails. Any thrown error goes through shapeError, and KevboxLiveErrors swaps the whole box for "Could not load KevBox Live errors". The test intent at plan:667 does not cover a failed read.

What the finding gets wrong is the claim that this breaks the box. The box only appears inside the customer dialog on the dashboard, and every dashboard page already needs Sheet1. The dashboard layout clears the cache on each page load and then calls fetchSheet1Data() with no fallback. If the workbook can't be read, the customers page fails before the dialog can open. The dialog itself is built from a Sheet1 customer row (customer-detail-dialog passes `customer` to KevboxLiveSection). fetchSheet1Data also keeps a 5-minute cache, so when the box sends its request, the workbook was usually read without error a few seconds earlier and the route gets the cached copy.

For the route's read to fail while the box can still be seen, the workbook would have to break after the page loaded and the cache would have to expire, all while the dialog is open. Even then, a page refresh shows the dashboard's own error, so Kevin would see that the workbook is broken. The route does not add a new failure mode a user would hit, and the "hidden exactly when a customer can't watch" scenario does not survive the existing dependency. A try/catch around the Sheet1 read would be a small hardening, not an important gap.

### db-4 [minor]

**Claim.** Proof check (d) runs the kevbox_admin select, insert and update checks on live_watch_incident (RLS on, no policies) but does not first check that kevbox_admin has BYPASSRLS on the local stack. 0000_roles.sql treats that attribute as optional. **Refuter.** The facts the finding cites are accurate, but its conclusion is wrong. 0000_roles.sql does treat BYPASSRLS (the attribute that lets a role skip row-level security, RLS) as optional. prove-member-playlist-rls.sh does guard for it. ### check-4 [minor]

**Claim.** alerted_at means both 'can't-watch message sent' and 'silently marked because another incident was already alerted', so toClearAlert cannot apply AC-22's rule 'no watching-again for an incident that never had a can't-watch message sent'. Example: TV1 messaged, TV2 silently marked, TV1 goes grey before it clears. TV2 clearing then sends a watching-again message for an incident no can't-watch message ever covered.

**Refuter.** The plan matches what the finding describes. Without grey, the TV2 message is what the spec asks for. With grey, the plan still follows the spec's own definitions and does what the spec intends.

1. The spec gives `alerted_at` both meanings itself. Spec lines 181-182 say incidents that open while the customer already has an open alerted incident "get `alerted_at` set with no message". So a silently marked incident counts as "alerted" by design. This is not a mix-up the plan introduced.

2. The first sentence of AC-22 (spec 266) requires the message in this scenario. It says one watching-again message goes out "when a customer's last open alerted incident clears". 3. The case without grey shows the design already sends watching-again messages for silently marked incidents. Say TV1 is messaged, TV2 is silently marked, TV1 clears first (the user is skipped because TV2 is still open and alerted, plan 496), then TV2 clears. That last step sends the watching-again message, and only TV2's clearing can trigger it. The second sentence of AC-22 ("never had a can't-watch message sent") is about the customer not being told something they were never told. Here the customer was told: TV1's message covered them. With grey, TV1 will never get its own watching-again message (AC-26). That makes TV2's message the one and only "watching again" that answers the earlier "can't watch". 4. The scenario needs one TV to stay broken for 7 days while another stays open and then clears. Even then, the result is one correct-looking green message, so "minor" would be an overstatement too.

The finding has two smaller errors as well. The `toClearAlert` comment is on plan line 395, not 397 (line 397 is `members`). And it reads the second sentence of AC-22 apart from the first sentence and from spec 182.
