# 0.7-encrypted-proxy: gap report

Hunt run 2026-11-10 on the spec `docs/superpowers/specs/2026-11-10-0.7-encrypted-proxy-design.md`
and the plan `docs/superpowers/plans/2026-11-10-0.7-encrypted-proxy.md`. Four slices (relay,
appwire, kevbox, server); all four hunters returned. 24 raw gaps, 23 after removing duplicates:
16 confirmed (1 critical, 5 important, 10 minor), 0 disputed, 7 refuted, 0 unverified. 28 agents.
Severities below are the refuters' corrected ones.

## Confirmed

### server-1 (critical): the GnuTLS Squid sends only the leaf certificate

- **Claim:** Debian's GnuTLS Squid 6.13, which persovps runs, sends only the leaf from
  `tls-cert=fullchain.pem`, never the intermediate. Android (which never fetches a missing
  intermediate, and Core's bundled roots hold none) and curl then refuse the real Let's Encrypt
  certificate. Both proofs use a one-level test CA, so the build goes green and the first failure
  is runbook step 6 on the live server.
- **Evidence:** throwaway `debian:trixie` container, root → intermediate → leaf: `openssl s_client
  -showcerts` lists only `0 s:CN=northcache.uk`, verify code 21; curl exits 60; `tls-cafile`
  changes nothing. Same files on `squid-openssl` 6.13: both certificates, verify 0, curl 200.
  persovps runs `6.13-2+deb13u4` GnuTLS flavour.
- **Refuters (2, both critical):** the first reproduced it in its own container (verify 21 with the
  root trusted). The second: the spec's central server decision fails as written and reopens the
  TLS-version findings measured on the GnuTLS build; step 6 would catch it only after the nginx
  pin, the certificate and a Squid restart in the live window.
- **Folded:** decided at gap fold (orchestrator, verified 2026-11-10 in a container): persovps moves
  to `squid-openssl`. Spec Scope, AC-4 (squid-openssl, `tls-min-version=1.2`, full chain served)
  and a new Decision replacing the GnuTLS findings; the Let's Encrypt Decision notes the
  intermediate. Plan: tech stack line; Task 9's `squid.conf` block gains `tls-min-version=1.2`
  and a new comment; `check-tls-proxy.sh` checks the leaf and intermediate are sent and verify
  against the root alone; `test-in-container.sh` installs `squid-openssl`, checks `squid -v`, and
  uses a three-level chain (and for the reconfigure swap); new runbook step 6 (install
  `squid-openssl`, check, undo) inside step 7's restart window, later steps renumbered; Task 1's
  `make-test-certs.sh` signs servers with an intermediate; Task 10 pushes the container's root
  alone, so playback proves the intermediate is sent.

### server-2 (important): a port-based ban on 443 blocks every persovps website

- **Claim:** `port = 38129,443` on persovps's stock nftables action bans the address from port 443
  on every server address, so all 11 nginx sites go dark for that household for an hour, bans set
  off on plain 38129 included. An expired customer's TV still sending its login sets it off. AC-5
  said "as today"; no decision accepted it.
- **Evidence:** `defaults-debian.conf` `banaction = nftables` (multiport: source and port only);
  `jail.local` `[squid-auth] port = 38129`; the filter counts 407s with a username; the refresh
  drops expired logins; plan Task 9 Behaviour 7 only stated the side effect.
- **Refuter (important):** every claim checked against the live config, read only. The spec's own
  case for Approach C is that blocking the proxy must not block kevbox.dev.
- **Folded:** decided at gap fold: the 443 ban matches destination `45.146.255.87` only through a
  custom nftables action beside the stock 38129 ban. Spec Scope, AC-5 and a new Decision. Plan
  Task 9: new file `kevbox-squid-tls-nft.conf` (verbatim, written against fail2ban 1.1.0's
  `nftables.conf` read from persovps), the jail drop-in now adds a second action instead of
  `port = 38129,443`, a container ban test (443 on the TLS address refused, 443 on another address
  still answers, 38129 refused, unban restores), runbook step 8's check and live test (kevbox.dev
  still loads while banned), Behaviour 7's statement, step 12's jail undo.

### relay-2 (important): Task 10 switches engines through hidden settings

- **Claim:** check (b) said to switch ExoPlayer/mpv "in the app's settings"; KevBox Live hides those
  rows and fixes live playback to ExoPlayer, so the mpv half of AC-22 could not be done as written.
- **Evidence:** `LiveOnlySettings.kt` hides `vp_live_engine*`/`vp_vod_engine*`, `LIVE_ENGINE =

- **Refuter (important):** confirmed; an unattended tester could log the mpv half as impossible,
  and mpv takes its proxy by its own path, which is AC-22's point.
- **Folded:** Task 10 check (b) now uses the full-screen engine pill, names catch-up as a second
  route, and says the settings rows are hidden.

### relay-3 (important): the relay's thread pool may be capped

- **Claim:** Task 1 said only "a pool of daemon threads". Each connection holds its threads for
  life, and the stream, guide, parallel logo loads and OkHttp's idle keep-alives all go through the
  relay, so a fixed pool would silently stall new connections. Every test used one connection.
- **Evidence:** plan Task 1 Behaviour 2-3; spec "How it works" step 2; Core `ProxyConfig.kt`
  36-41 (Coil and ExoPlayer share one client).
- **Refuter (important):** confirmed; the gap is in the behaviour wording, not only a test, and a
  stall would be felt on real TVs.
- **Folded:** Task 1 Behaviour 2 requires a pool with no upper bound (cached, never queued) and says
  why; the first test intent gains "with 32 connections held open, a 33rd still round-trips"
  (merged, still 5 intents).

### appwire-1 (important): the release check passes when kevbox is behind

- **Claim:** `check_relay_min_version` warned and passed on a missing line, but `liveVersion.ts`
  already exists on kevbox `main` without it and `release.sh` reads that checkout, so a release
  run before 0.7's kevbox code is there ships unchecked.
- **Evidence:** `release.sh:67` `kevbox_repo="$HOME/projects/kevbox"`, checked out on `main`;
  `liveVersion.ts` has three constants and no `RELAY_MIN_VERSION`; "After the build" ran the
  release before any step put 0.7's kevbox code there. Found by two hunters.
- **Refuter (important):** the `check_error_codes_match` parallel fails: there a missing file means
  "no checkout", here file-without-line means "kevbox is behind", which should refuse.
- **Folded:** spec's `RELAY_MIN_VERSION` Decision; Task 3 Behaviour 3 (file present without the line
  refuses; only a missing file warns), the die message, the release-check test intent (one more
  case, same intent); "After the build" step 3 brings 0.7's kevbox code into the checkout first.

### kevbox-1 (important): an env edit never reaches the running web app

- **Claim:** `kevbox.service` reads `/etc/kevbox-www/env` only at start, and no step restarts it
  after a `VPS_PROXY_TLS_*` edit. The switch and Send then write by the old list while the refresh
  writes by the new one, so the off switch and a name or address change flip TVs back and forth,
  each flip a channel restart.
- **Evidence:** `kevbox:deploy/kevbox.service` `EnvironmentFile=` with `ExecStart npm run start`;
  the refresh is a fresh oneshot; plan Task 6 Behaviour 1 justified "no caching" by the refresh
  only; runbook step 8 and the `env.example` text named no restart.
- **Refuter (important):** confirmed; an emergency "empty the list" is when Kevin is most likely to
  press the switch or Send, which refills the address.
- **Folded:** spec Decision on the client list; Task 6 Behaviour 1 and the verbatim `env.example`
  (restart line); runbook steps 9 (do and undo) and 11 (rollout, name or address change);
  "After the build" step 4.

## Refuted

- **relay-1 (important → refuted):** Task 10 "cannot run" because the container cannot reach a fake
  panel bound to 127.0.0.1/10.0.2.2. Refuter: `--allow-dst <fake panel's range>` already tells the
  builder to put the panel on a private address the container reaches (the Docker bridge); the
  panel is Task 10's own setup, and a wrong address shows at once as a channel that will not play.
- **relay-4 (important → refuted):** closing sockets on retarget leaves the channel in an error
  state instead of restarted. Refuter: 0.6's VPN path already kills the stream socket and restarts
  1 s later, which `ChannelRestarter` exists for; the player plays from its buffer; the relay keeps
  its port, so reconnects reach the new target. What is left is a missing test for a guessed
  interaction.
- **server-3 (important → refuted):** Task 10 cannot reach the container's plain port through one
  `--publish`. Refuter: `http_port 38129` listens on every container interface, `--keep` prints the
  container name, the emulator reaches the bridge address through the host, and checks (c)/(d) read
  the access log; worst case the implementer reports, as Task 10 says.
- **relay-5 (minor → refuted):** check (c)'s "plays again by itself" contradicts the restart rule.
  Refuter: Core's engine retries a channel that did play on a backoff ladder for about two minutes,
  each retry through the relay, so it does play again with no key press.
- **relay-7 (minor → refuted):** the access log cannot show which port a request used. Refuter:
  line 683 lists several kinds of proof, `/proc/net/tcp` among them; (c) and (d) need no port
  distinction; (a) is proved by `/proc/net/tcp` plus the log.
- **appwire-4 (minor → refuted):** no test pins `resume()` before the coordinator's collectors.
  Refuter: a missing test with little user impact; the race window is a loopback bind, an
  unreachable expiry check is dropped without changing state, playback is not affected.
- **server-8 (minor → refuted):** AC-28 is not checked on the plain port. Refuter: every AC-28
  setting is server-wide, so the TLS-port check covers both ports; a missing test with no realistic
  silent failure.
