### Notes

1. **mpv does not log in to an authenticating proxy, plain or relay.** With the encrypted address
   cleared (14:47:41.985; listener gone), E2E News Three pinned to mpv at 14:49:30 failed the same
   way through the plain port: `HTTP error 407`, Squid `TCP_DENIED/407 … -` then `NONE_NONE/000`,
   until Core's ladder fell back to ExoPlayer at 16:49:47.8 TV and played. On this PC, `ffmpeg
   n9.0.2` (the FFmpeg version in Core's mpv) with `-http_proxy http://kbtest:<password>@172.17.0.3:38129`,
   with and without Core's reconnect options from the `mpv_open` log line, and desktop `mpv
   v0.41.0` with `--http-proxy=` the same, all got Squid's 407 and then sent the login (`TCP_MISS/200
   … kbtest` at 14:47:25, 14:50:25, 14:50:34). So it is Core's Android mpv build that drops the
   connection after the 407 instead of answering it. It matches the live `live_error` rows of
   2026-10-25: every `http_407` row then was mpv on the proxy, with the same Squid pattern. Before
   0.7 this already meant that a proxy customer who switches a channel to mpv (the HUD pill, or
   catch-up, which starts on mpv) gets an error, or ExoPlayer after about 17 s when the pin came from
   an earlier choice. 0.7 neither causes nor fixes it. Core is not forked, so the fix is out of
   reach here; see "Open items".
2. **Diagnostic: mpv's traffic through the relay, with the login rule lifted.** To see whether the
   relay itself carries mpv, I changed one line of the running container's test copy only:
   `http_access allow authed e2e_dst` became `http_access allow e2e_dst` (no login needed for the
   fake panel), then `squid -k reconfigure` at 14:51:03. Encrypted address back at 14:51:14.558,
   pill to mpv at 14:51:42. mpv opened the stream through the relay: `event: file-loaded`
   16:51:44.416 TV, `playback-restart` 16:51:44.487, `LiveEngine: 'E2E News Three' opened on mpv`
   16:51:45.0, Squid `TCP_MISS_ABORTED/200 16122021 GET …/103.ts -` over 443 (`tls_new` 19 → 24,
   `plain_new` unchanged). The picture then failed on the emulator itself: `h264_mediacodec:
   MediaCodec 0x0 failed to start`, software decoding, then `[vf:fatal] Cannot convert
   decoder/filter output to any format supported by the output` and `[cplayer:fatal] Could not
   initialize video chain` (screen: `This TV's video decoder is busy.`). This AVD runs with hardware
   decoding off (the `run-emulator` mitigation for the AMD crash), and Core's mpv output needs
   MediaCodec. I put the test copy back at about 14:52 (`diff` against the saved copy empty; a
   no-login request then got 407). So the relay carries mpv's bytes both ways, but this emulator can
   never show mpv's picture, and with the login rule in place mpv stops at the 407 (note 1). Catch-up,
   the plan's second mpv route, was not tried: the fake panel has no archive.
3. **The channel comes back by itself only while the player is still trying.** The re-tune after a
   route change (`ChannelRestarter`, 0.6 AC-40) acts only on a channel that plays by 0.4's play test.
   When the address returned after 65 s, the player had given up 15 s after the break and showed its
   error screen, so nothing re-tuned it; Retry played it at once. When the address returned after 5
   s, ExoPlayer's own retry reached the new target and played with no key press. Spec AC-19 asks for
   the restart "by 0.6's AC-40 rule", so the code does what the spec says; the plan's check expected
   more. A blocked address that comes back minutes later leaves the customer on the error screen
   until they press Retry or change channel. See "Open items".
4. **Logs.** The run's logcat held none of: the test proxy password, `kbtest`, `northcache`,

   <class>`: `SSLHandshakeException` 21 times (checks d and i), `SocketTimeoutException` twice,

## Open items for Kevin

- **mpv on the proxy (note 1).** Not a 0.7 regression and not fixable without touching Core.
  Options: leave it (ExoPlayer is KevBox Live's live engine, and a pinned mpv choice falls back to
  ExoPlayer after about 17 s); ask upstream Core to make its mpv answer a proxy's 407; or let the
  relay add the login itself so mpv needs none. The last one changes 0.7's design (the relay
  "never adds a byte", and any app on the TV could then use the proxy through it), so it is a
  decision, not a fix.
- **Recovery after a long block (note 3).** Options: keep 0.6's rule (Retry or a channel change
  brings it back), or have a route change also re-tune a channel whose last failure was a network
  error on screen. The second is a change to 0.6's `ChannelRestarter`.
