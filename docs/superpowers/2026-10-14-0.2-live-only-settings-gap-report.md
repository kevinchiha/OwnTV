### player-guide-1 (important)

**Claim.** Task 8 ties the grid's CH+/CH− handler to fixed key codes, but the app decides what a remote button does from the Remote shortcuts list, not from the key code. As planned, the grid ignores the member's own button assignments: a CH+ reassigned to another action (say Open Search) still jumps 10 channels in the grid and the shortcut never fires. Rewind/fast-forward (Core's default page keys) do nothing in the grid. Holding CH+/CH− (default: jump to first/last) either does nothing or repeats the 10-channel jump. That contradicts the help text on the Remote shortcuts page, which the spec keeps. The plan's constraint even names chNavPaging as treating fixed 'channel keys', which it does not.

**Evidence.** Plan Task 8 constraint: 'Key the handler on the actual CH+/CH− key codes Modifier.chNavPaging ... treats as channel keys'. ChNavPaging.kt:57-91 looks the action up from remote.bindings by keyCode and press length (PAGE_TOWARD_FIRST/LAST, JUMP_TO_FIRST/LAST, other actions passed to remote.dispatch). RemoteShortcuts.kt:48-55: Rewind/FF short = PAGE_*, CH±/Rewind/FF long = JUMP_TO_*. Core strings_settings.xml:158: 'By default, CH+/CH− and rewind/fast-forward page browsing lists; holding them jumps to the first or last item.' GuideStage.kt:731-739 already applies Modifier.chNavPaging to a guide list. GuideChannelSteps.target takes only a towardFirst boolean, with no case for an action or a long press.

**Touches.** task-8, AC-24, fn:GuideChannelSteps.target, fn:chNavPaging, code:RemoteShortcutBindings.defaults, artifact:settings_remote_shortcuts_help, decision:remote-shortcuts

**Refuter.** I could not refute any part of the finding. Every claim checks out against the files.

1. The plan's Task 8 tells the builder to handle the fixed CH+/CH− key codes "Modifier.chNavPaging treats as channel keys". chNavPaging does no such thing. It looks up the pressed key in the member's Remote shortcuts list (remote.bindings), picks the short- or long-press entry, and then acts on that entry's action. Any action other than paging goes to remote.dispatch.

2. Core's default list gives the paging actions to four buttons: CH+, CH−, rewind and fast-forward. A long press on any of them means jump to the first or last item. GuideChannelSteps.target only takes a towardFirst flag, so it has no case for a long press or for any other action.

3. The shell's own shortcut handler (OwnTVShell.kt:1007-1047) runs non-paging shortcuts when the key reaches it, and skips paging actions because the panes handle those. If a member reassigns CH+ to, say, Open Search, a grid handler keyed on the CH+ code still jumps 10 rows. Because the plan says it consumes the key when it moves, the key never reaches the shell, so the shortcut never fires. Rewind and fast-forward get no handler in the grid at all.

4. The Remote shortcuts help text (Core strings_settings.xml:158) promises that CH+/CH− and rewind/fast-forward page through lists and that holding them jumps to the first or last item. The grid as planned would break that promise.

The spec's AC-24 is written in terms of the CH+ and CH− buttons, so the plan does match the spec's wording. Still, the plan's constraint misdescribes the existing modifier and steers the builder away from it. The modifier already does the binding-aware version, and GuideStage.kt:731-739 already uses it for a guide list. With default bindings and a short press the plan works. Rewind/fast-forward and long presses are a gap even on defaults, and reassigned buttons misbehave. "Important" is a fair severity: the fix is cheap (use the existing modifier), but as planned it ships behaviour the help page says is wrong.

### sources-1 (minor)

**Claim.** Task 9 orders replaceFor after updateSource and says nothing about failure. If replaceFor throws, is cancelled while it waits for GuideFeeds' mutex, or the process dies between the two calls, the old feed keeps downloading forever. In the throw and cancel cases the UpdateInPlace step also skips resync, so the new server's channels never sync. No later run repairs either, because the old guide URL exists only in the overwritten source row and planReconcile no longer sees a difference.

**Evidence.** Plan Task 9 behaviour 3: 'calls guideFeeds.replaceFor(existing, updated) after updateSource'. CoreLocalSources.kt:89-95 overwrites url/username/password, the only inputs to the guide URL (XtreamClient.kt:783-790). PlaylistReconciler.kt:269-270 runs update, then resync, with no catch, and KevBoxCoordinator.kt:207 swallows the throw. ReconcilePlanner.kt:93 only plans UpdateInPlace while the fields still differ. GuideFeeds.kt:83 mutex.withLock is a cancellable wait while ensureAll holds the lock. Fix: run replaceFor before updateSource (new URLs come from the entity about to be written), or catch its errors with quietly, and say which in the plan.

**Touches.** task-9, AC-28, fn:GuideFeeds.replaceFor, fn:CoreLocalSources.update, fn:PlaylistReconciler.reconcile, fn:planReconcile

**Refuter.** The mechanism the finding describes is real, but it only bites in rare cases, so I'm keeping it and lowering it to minor.

What checks out:
- The plan, Task 9 behaviour 3, puts `replaceFor(existing, updated)` after `updateSource` and says nothing about what happens if it fails.
- `CoreLocalSources.update` overwrites `url`, `username` and `password` in place. The plan's own Task 9 intro says that is where the old guide URL is lost.
- In `PlaylistReconciler`, the UpdateInPlace step runs `update` and then `resync` inside a try/finally with no catch. If `update` throws, `resync` never runs.
- `planReconcile` only plans UpdateInPlace while the stored fields differ from the row (line 93). Once the row is written they match, so no later run calls `replaceFor` again. The old URL is gone, and nothing can work out which feed to remove.
- `GuideFeeds.removeFor` takes `mutex.withLock` outside `NonCancellable`, so waiting for the lock can be cancelled. `ensureAll` holds the same lock.

Corrections:
- The swallowed exception is caught in `SingleFlight.guarded` (KevBoxCoordinator.kt:273-281), not at line 207. Line 207 is a bare `reconciler.apply` call. The effect is the same: the error is dropped and the next check finds nothing to redo.
- "The new server's channels never sync" goes too far. CoreLocalSources' KDoc says Core's own auto-refresh syncs sources linked to the active profile, so the channels probably sync later anyway. I could not check that inside Core.

Why minor:
- A throw needs a Room or store error inside `replaceFor`.
- The reconcile runs in `scope.async` on the coordinator's scope. It is only cancelled when that scope is cancelled, which in practice means the app is shutting down.
- Process death has to land in the gap between two local database calls.
- In each case the result is one leftover guide download using the old login. The user can still delete it by hand: its URL no longer matches the playlist's guide URLs, so under AC-26 it shows as a guide added by hand. Nothing breaks.

The fix is cheap and correct, and the plan should name it. Either remove the old feeds before `updateSource`, or work out the old URLs first and run the removal under `quietly`. Before is safe: if `updateSource` then fails, the fields still differ, so the next run retries the update and the resync.

### more-previews-ship-1 (important as filed)

**Claim.** tv-install.sh never reads the TV's installed versionCode. It reads versionName and recomputes the code with version.sh. If the TV's build was installed with any other code (the 99999999 fallback that build.gradle.kts uses whenever VERSION_CODE is unset, or a hand-set code from the lost tvbuild.sh), 'adb install -r' fails with a downgrade error and the task stops. **Refuter.** The facts the finding quotes are accurate. The plan script reads only versionName (line 823), computes the code with version.sh (line 825), and build.gradle.kts sets versionCode and versionName from separate env vars. The failure it predicts mostly does not happen, though.

1. The 99999999 fallback example is wrong. 2. Every published build already uses this rule. release.sh line 101 computes the code with `version.sh code "$version"` and exports both values at line 132. Any APK from the normal release path has name and code in step, so "using the TV's own version gives the same code" is true for release builds.

Even if it did, nothing is lost. `set -euo pipefail` makes the script stop on adb's downgrade error, before force-stop and without uninstalling, so the TV keeps the old app and Kevin's data. The error is visible, and the script takes the version as its first argument, so the orchestrator can rerun it with a higher version. Task 13 is supervised and ends with Kevin checking the TV himself, so a failure there would not go unnoticed.

At most this is a minor hardening idea (read versionCode from dumpsys and compare), not an important gap.
